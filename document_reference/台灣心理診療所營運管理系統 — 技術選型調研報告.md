# 台灣心理診療所營運管理系統 — 技術選型調研報告

## TL;DR

- **推薦主 Stack（Stack A，首選）**：FastAPI + SQLAlchemy 2.x + Alembic + PostgreSQL（Railway 內建）+ Redis + Dramatiq worker + Railway Cron Jobs（用於每日/每月批次）+ Next.js 14 App Router (TypeScript) + FullCalendar + Auth.js v5（前端 session）/ FastAPI 自簽 JWT（後端 API 驗證） + Sentry。預估 Railway 月費約 **USD 17–25**，安全落在 NT$3000 上限內。
- **次選 Stack（Stack B，若行政後台介面省事優先）**：Django 5 + Django Ninja + Django Admin + PostgreSQL + APScheduler（小量背景任務）+ Railway Cron Jobs + Next.js 14 + Clerk Free Tier（含 50,000 MAU 免費額度）。Admin Panel 自動生成可節省 2–4 週開發工時，代價是 Claude Code 對 Django 信號/middleware 的程式碼生成品質略遜於 FastAPI。
- **整體開發複雜度**：中等偏高（核心難點是狀態機帳務 + 三維空間預約 + 排程 + 個資加密 + Audit Log）。粗估 Claude Code 全程協作下 **MVP 約 6–9 週工程量**，正式上線含使用者驗收約 3–4 個月。

## Key Findings（決策摘要）

1. **後端應選 FastAPI 而非 Django**：給 Claude Code 等 LLM 用，FastAPI 的型別註記（Pydantic）讓 LLM 產生的程式碼幾乎一次到位、錯誤訊息明確；Django 的「魔法」（settings、apps、signals）反而容易讓 LLM 產出看似對但執行錯的程式碼。Django 唯一壓倒性優勢是 Admin Panel，但本案需自製日曆 UI、狀態機帳務、權限分層，Admin 幫不上太多忙，反而把架構綁死在 Django ORM 上。
2. **前端應選 Next.js App Router 而非純 SPA**：理由不是 SEO（內部系統不需要），而是（a）Auth.js v5 + Server Components 可直接在 Server 端做權限檢查、隱藏資料；（b）Railway 對 Next.js 部署有一鍵模板；（c）FullCalendar、React Hook Form、shadcn/ui 都在 Next.js 生態下測試最完整。若團隊極度排斥 Server Component 心智負擔，Vite + TanStack Router 是合理替代（Railway 工程師 Victor Ramirez 在 2026-04-03 官方部落格《Moving Railway's Frontend Off Next.js》宣布：「Railway's entire production frontend no longer runs on Next.js. The dashboard, the canvas, railway.com, all of it now runs on Vite + TanStack Router, and we shipped the migration in two PRs with zero downtime.」）。
3. **背景排程應用「混合策略」**：每日結算、月報表、流失掃描 → **Railway Cron Jobs（獨立服務）**；預約提醒、PDF 產出等使用者觸發的延遲任務 → **Dramatiq + Redis**（FastAPI 進程內 enqueue，獨立 worker 服務消費）。**避免使用 APScheduler 單機嵌入**（多 replica 會重複觸發、不持久化）、**避免 Celery**（設定複雜度與 LLM 出錯率對小團隊不划算）、**pg_cron 僅作為備援**（Railway 內建 PG 不一定預載此擴充，且任務只能跑 SQL/HTTP，不適合複雜 Python 邏輯）。
4. **認證應採「混合方案」**：前端用 Auth.js v5 處理登入流程與 session cookie；後端 FastAPI 自簽 JWT 處理 API 驗證與 RBAC。**不要為了 20 個使用者的內部系統採購 Clerk/Auth0**（Clerk Pro USD 20/月起、Logto Pro + RBAC 達 USD 56/月，且醫療資料考量資料主權，把使用者資料外送雲端風險不對等）。Supabase Auth 只在你同時用 Supabase DB 才划算，不適合本案 Railway 部署。Keycloak/Logto 自架對 20 人系統屬於 over-engineering。
5. **三維空間預約應採「單表 + EXCLUDE GIST 約束」**：用 PostgreSQL 原生 `tstzrange` 與 `EXCLUDE USING GIST (room_id WITH =, time_range WITH &&)` 在資料庫層強制空間時段不重疊。比應用層檢查 + 鎖效能高、零 race condition、跨年自動處理。PostgreSQL 官方範圍類型文件直接給出此範例（postgresql.org/docs/current/rangetypes.html），並指出「You can use the btree_gist extension to define exclusion constraints on plain scalar data types, which can then be combined with range exclusions for maximum flexibility.」
6. **帳務不可變性用「標準 audit table + 軟鎖定欄位」**：不要採完整 Event Sourcing（對 20 人診所過度設計）。每張流水帳寫入時透過 trigger 寫入 audit log，並用 `locked_at` 欄位 + 應用層守衛實作「核銷後不可改」。Row-Level Security 對本案幫助有限（角色已在應用層判斷），但建議啟用 pgAudit 擴充作為合規證據。

## 1. 後端框架比較

| 維度 | FastAPI + SQLAlchemy + Alembic | Django + DRF | Django Ninja | Flask |
|------|--------------------------------|--------------|--------------|-------|
| Admin Panel | ❌ 需自寫或用 sqladmin | ✅ 原生強大 | ✅ 共用 Django Admin | ❌ |
| ORM 成熟度 | SQLAlchemy 2.x 業界最強 | Django ORM 內建、夠用 | Django ORM | 無 |
| Migration | Alembic（需手動 init env） | makemigrations 自動 | makemigrations | 無 |
| 型別/驗證 | Pydantic v2，OpenAPI 自動 | DRF serializer 較囉嗦 | Pydantic（Django 內！） | 無 |
| **LLM/Claude Code 友善度** | ⭐⭐⭐⭐⭐ 型別強、樣板少 | ⭐⭐⭐ 慣例多、隱性魔法 | ⭐⭐⭐⭐ 折衷 | ⭐⭐⭐ |
| 背景排程整合 | Dramatiq/Celery/APScheduler 皆可 | django-celery-beat 成熟 | 同 Django | 自由 |
| Railway 部署 | Nixpacks 一鍵 / Dockerfile | Nixpacks 一鍵 | 同 Django | 一鍵 |
| 學習曲線 | 低 | 中 | 低 | 低 |
| 開發速度（含 Admin） | 中（無 Admin 是負擔） | 高 | 高 | 低 |

**決策理由（為什麼選 FastAPI 而非 Django）**：
- 本案核心痛點不是 CRUD（Django 強項），而是「狀態機驅動的帳務流轉」與「複雜資料處理」。FastAPI 的 Pydantic v2 + Python type hints 讓 Claude Code 生成「狀態流轉守衛、空間衝突檢查、AES 加密 helper」這類有強型別約束的程式碼時，幾乎一次到位；Django 的 `model.save()` override + signals 模式會讓 LLM 寫出難以追蹤的副作用程式碼。
- Admin Panel 看似誘人，但本案前台已經是專屬 Next.js UI；行政人員、心理師都從前台操作，Admin Panel 只剩管理員偶爾撈資料用——這用 [sqladmin](https://aminalaee.dev/sqladmin/) 或 [FastAPI Admin](https://github.com/fastapi-admin/fastapi-admin) 都能補上，不值得為此鎖死整個技術棧到 Django。
- 「Django Ninja」是合理折衷（FastAPI 體驗 + Django Admin + Django ORM），但生態仍小，LLM 訓練資料量明顯少於 FastAPI 與 Django 本體；Claude Code 在 Django Ninja 邊角案例（async middleware、auth backend）容易產出舊版 DRF 寫法。
- Flask 在 2026 年已不建議用於新專案：缺乏型別、async 支援差、生態散落、LLM 容易產生過時的 Flask 0.x / 1.x 寫法。

**官方文件連結**：
- FastAPI: https://fastapi.tiangolo.com/
- SQLAlchemy 2.x: https://docs.sqlalchemy.org/en/20/
- Alembic: https://alembic.sqlalchemy.org/en/latest/
- Django Ninja（次選）: https://django-ninja.dev/

## 2. 前端框架比較

| 維度 | Next.js 14 App Router | React + Vite SPA | Remix / React Router v7 |
|------|----------------------|------------------|------------------------|
| Railway 部署 | 一鍵模板，Nixpacks 偵測 | 靜態 + 反向代理 | Nixpacks 偵測 |
| FullCalendar 支援 | ✅ 官方 React wrapper | ✅ | ✅ |
| 表單處理 | React Hook Form + Zod 主流 | 同 | 同 |
| 認證生態 | Auth.js v5 原生整合 | 需手動串 | 有 remix-auth |
| Server Component RBAC | ✅ Server 端隱藏資料 | ❌ 全 client | 半（loader） |
| 開發體驗 | 較重，build 慢 | 極快 HMR | 折衷 |
| **LLM 友善度** | ⭐⭐⭐⭐ App Router 範例多 | ⭐⭐⭐⭐⭐ 模式單純 | ⭐⭐⭐ v7 較新 |

**決策理由（為什麼選 Next.js App Router）**：
- 醫療系統最在意「不讓非授權使用者看到資料」。Next.js Server Component 可在 Server 端 fetch 完資料、過濾欄位、才送 HTML 到 client，這比純 SPA「先送資料、JS 再隱藏」安全得多。
- Auth.js v5 與 Next.js Middleware 整合可在路由層攔截未登入請求，省去寫 ProtectedRoute HOC。
- 注意：Railway 自家前端 2026 年 4 月從 Next.js 遷至 Vite + TanStack Router，依官方部落格描述：「Frontend builds had crept past 10 minutes. Six of those minutes were Next.js alone, half of it stuck on 'finalizing page optimization.'」但本案規模遠未到此痛點（單一專案、build 預期 < 2 分鐘）。

**官方文件連結**：
- Next.js: https://nextjs.org/docs
- FullCalendar React: https://fullcalendar.io/docs/react
- React Hook Form: https://react-hook-form.com/
- Zod: https://zod.dev/

**日曆套件選擇：FullCalendar 而非 React Big Calendar**：
- FullCalendar 有官方 React wrapper、原生支援「Resource Timeline View」（即「空間 × 時段」二維檢視），這正是本案空間預約 UI 的核心。
- Resource View 屬於 FullCalendar Premium 功能（一次性 USD 480 年費 / standard developer license）。若預算緊，可先用 standard 版的 timeGrid 自製 column-per-room view，或改用免費的 React Big Calendar + 自製 resource layout。
- React Big Calendar MIT 免費，但缺 Resource Timeline，需自己拼 view。

## 3. 資料庫與 Redis

| 方案 | 月費（小型）| 優點 | 缺點 | 適合此案？ |
|------|------------|------|------|-----------|
| Railway PostgreSQL | ~USD 5–8 | 同 Project 私網、零延遲、一鍵備份 | 區域選擇少（US/EU 為主） | ✅ 首選 |
| Supabase Free | USD 0 起 | Auth、Storage、Realtime 整合 | 7 天閒置會 pause、與 Railway 跨網路 | ❌ |
| Neon | USD 0 起 | Branching、Scale-to-Zero | 與 Railway 後端跨網路延遲；冷啟動 ~500ms | ❌ |

**決策理由（PostgreSQL on Railway）**：把 DB 與 FastAPI 放同一個 Railway Project，可走私網（`postgres.railway.internal`），延遲 < 1ms，且共用環境變數注入。Supabase/Neon 雖然功能多，但本案不需要 Realtime、Branching；跨網路反而增加 latency 與排錯複雜度。

**Redis 是否需要？** → **需要，但僅 1 個小實例（256 MB 內）約 USD 3–5/月**。用途：
1. Dramatiq message broker（替代 Celery + RabbitMQ）。
2. Session/快取（可選，本案規模其實 PG 就夠）。
3. Rate limiting（個資法相關，建議對登入 endpoint 加限速）。

## 4. 背景排程（重點章節）

| 方案 | 持久化 | 多 replica 安全 | Railway 部署 | LLM 友善度 | 學習曲線 |
|------|--------|----------------|-------------|------------|---------|
| **Railway Cron Jobs**（獨立服務） | N/A（每次啟動容器） | ✅ Railway 排程器保證單次 | ⭐⭐⭐⭐⭐ 內建設定 | 高 | 極低 |
| **Dramatiq + Redis** | ✅ Redis 隊列 | ✅ | 中（需獨立 worker service） | 高 | 低 |
| **Celery + Redis** | ✅ | ✅ | 中 | 中 | 高（beat/worker 概念多） |
| **APScheduler 內嵌** | 可選 SQLAlchemy job store | ❌ 多 replica 會重複觸發 | ⭐⭐⭐⭐⭐ | 高 | 極低 |
| **pg_cron** | ✅ 在 DB 內 | ✅ | ❌ Railway 預設 PG 未啟用 | 中 | 中（只能跑 SQL/HTTP） |
| **RQ** | ✅ Redis | ✅ | 中 | 中 | 低 |
| **Huey** | ✅ Redis | ✅ | 中 | 低 | 低 |

**Railway Cron Jobs 關鍵限制**（官方文件 https://docs.railway.com/reference/cron-jobs）：
- 「The shortest time between successive executions of a cron job cannot be less than 5 minutes.」（不能小於 5 分鐘）
- 「Cron jobs are scheduled based on UTC.」（必須自行換算台灣 UTC+8）
- 「Railway does not guarantee execution times to the minute as they can vary by a few minutes.」（不保證準時，可能漂移幾分鐘）
- Cron Job 服務的容器啟動後執行完任務必須立即退出，否則下一次排程會被跳過。

**任務分配建議（決策表）**：

| 任務 | 推薦方案 | 理由 |
|------|---------|------|
| 每日結算（隔日 03:00 標記未取消預約為已執行） | **Railway Cron Job 服務**（cron: `0 19 * * *` UTC = 03:00 UTC+8） | 一天一次、需冪等、零延遲容忍度高 |
| 月報表自動產出（每月 1 日 06:00） | **Railway Cron Job 服務**（cron: `0 22 1 * *` UTC） | 同上，可能跑數分鐘長任務 |
| 流失預警掃描（每日 09:00） | **Railway Cron Job 服務** | 同上 |
| 預約提醒電訪清單產出（每日 18:00 隔日提醒） | **Railway Cron Job 服務** | 同上 |
| 「使用者點按鈕後寄信、產 PDF」之類延遲任務 | **Dramatiq + Redis** | 需要 enqueue from web 進程 |
| 失敗重試 | Dramatiq 內建（Cron 任務則靠應用層 idempotency + retry） | |

**為什麼不選 Celery？** Celery 在 Railway 上需要起兩個服務（beat scheduler + worker），加 Redis、加 backend storage，4 件事都要設定對。Dramatiq + Redis 只需要 1 個 worker 服務，且 LLM 在 Dramatiq 上產出的程式碼通常更簡潔（actor pattern）。Celery 的優勢只在「task graph 編排」這類複雜場景，本案沒有。

**為什麼不選 APScheduler 內嵌 FastAPI？** 它「看起來」最簡單（不用獨立服務、不用 Redis），但 Railway 一旦你想開多個 replica（為了部署不中斷），APScheduler 會在每個 replica 都觸發一次同樣的任務，必須加分散式鎖（PostgreSQL advisory lock 或 Redis SETNX）—— 那不如直接用 Railway Cron。

**為什麼不選 pg_cron？** Railway 自管 PostgreSQL 預設未啟用 pg_cron 擴充（需 superuser；Railway 用戶非 superuser），且任務只能跑 SQL 或 HTTP webhook，無法直接執行 Python（你的結算邏輯涉及狀態機、發信、寫 audit log，純 SQL 表達極不可讀）。

**官方文件連結**：
- Railway Cron Jobs: https://docs.railway.com/reference/cron-jobs
- Dramatiq: https://dramatiq.io/
- APScheduler（次選用法）: https://apscheduler.readthedocs.io/

## 5. 認證機制比較

| 方案 | 月費（本案 20 人） | 安裝難度 | RBAC 支援 | 醫療資料主權 | Railway 整合 |
|------|------------------|---------|----------|------------|-------------|
| **自建 JWT（FastAPI + python-jose + Auth.js v5 前端）** | USD 0 | 中（需自寫 refresh token） | 完全自訂 | ✅ 資料不出機房 | ⭐⭐⭐⭐⭐ |
| Clerk | USD 0（< 50,000 MRU 免費；Pro USD 20/月年繳起） | 極低 | ✅（Pro 起） | ❌ 使用者資料送美國 | 中 |
| Supabase Auth | USD 0（< 50k MAU 免費） | 低 | 有 RLS | ❌ 跨平台 | 差（與 Railway DB 衝突） |
| Auth.js v5（Next.js 套件，本身只是 client lib） | USD 0 | 低 | 自訂 callback | ✅ | ⭐⭐⭐⭐⭐ |
| Keycloak 自架 | Railway 上 ~USD 15–25（Java 吃記憶體） | 高 | ✅ 業界最強 | ✅ | 中（Java 容器） |
| Logto 自架 | Railway 上 ~USD 8–15 | 中 | ✅ 在 Pro plan add-on | ✅ | 中 |
| Logto Cloud | USD 0 起（Free plan 已於 2025-10 移除 RBAC 支援；Pro USD 24/月 + RBAC add-on USD 32/月 = USD 56） | 極低 | Pro add-on | ❌ | N/A |

> Logto 定價依據其 2025 年 9 月部落格《Logto pricing plan updates - September 2025》確認：「Pro is $24/month, with RBAC as a $32 add-on」，且 Free plan 自 2025 年 10 月 1 日起不再包含 RBAC。
> Clerk 自 2026 年 2 月定價更新後 Pro 為 USD 20/月（年繳），Hobby（免費）方案的免費配額由 10,000 提升至 50,000 MRU（Monthly Retained Users）per app（依 clerk.com/pricing 官方頁面）。

**強烈建議：自建 JWT + Auth.js v5 混合方案**

理由：
1. **20 人系統採購 SaaS 不划算**。Clerk Pro USD 20/月、Logto Pro + RBAC USD 56/月，一年 USD 240–700，相當於買斷一個簡單的內部 IAM。
2. **醫療資料主權**：台灣個資法雖未明文禁止把員工帳號送到境外，但心理診所使用者 = 心理師，其登入紀錄與診所運作行為有營業秘密性質。Clerk/Auth0 把使用者資料儲存在美國雲端，發生事故時你拿不到 forensic log，舉證困難。
3. **Auth.js v5 + FastAPI 的標準整合模式**：前端 Next.js 用 Auth.js v5 處理 Credentials Provider 登入、產生 session cookie，並在 `jwt` callback 內呼叫 FastAPI `/auth/login` 取得 FastAPI 簽發的 JWT，存於 `token.accessToken`，之後所有 fetch 帶 `Authorization: Bearer ...`。FastAPI 端用 `python-jose` 驗證自己簽的 JWT，並由 token claims 解出 role 做 RBAC。注意 Auth.js 自身的 JWT 預設為 **JWE 加密格式**，依 authjs.dev 官方文件：「JSON Web Tokens are encrypted (JWE) by default. We recommend you keep this behaviour.」這代表若想讓 FastAPI 直接驗證 Auth.js cookie，必須用 `fastapi-nextauth-jwt` 解密，這會把後端綁死在 Auth.js 的 JWT 格式上；更乾淨的作法是讓 FastAPI 自己簽自己的 JWT、Next.js 只是「保管者」。
4. **RBAC 實作要點**：在 FastAPI 端建一個 `RequireRole(["admin", "therapist"])` Depends，用 dependency injection 套到每個 endpoint。心理師只能看自己個案、行政可看所有預約但看不到病歷、管理員可看一切——這在自寫 JWT 下用 `if role == "therapist": query.filter(therapist_id == user.id)` 三行解決，比 RLS 直觀。

**何時改選 Logto/Keycloak？** 若未來要對接「健保署 IC 卡」或「醫師證 SSO」、或要支援多診所（每家一個 realm/tenant）——這時 Keycloak/Logto 的 OIDC 標準支援會省大量時間。本案目前不需要。

**官方文件連結**：
- FastAPI Security: https://fastapi.tiangolo.com/tutorial/security/oauth2-jwt/
- Auth.js v5: https://authjs.dev/
- python-jose: https://python-jose.readthedocs.io/
- Logto（備用）: https://docs.logto.io/

## 6. Railway 部署架構建議

**建議 Project 結構（單一 Railway Project 內 5–6 個服務）**：

```
[Railway Project: clinic-prod]
├── frontend (Next.js)            ← Node.js, ~$3-5/mo
├── backend (FastAPI uvicorn)     ← Python, ~$3-5/mo
├── worker (Dramatiq)             ← Python, ~$2-3/mo
├── cron-daily (Python script)    ← 排程觸發, ~$0.50/mo
├── postgres (Railway DB)         ← ~$5-8/mo
└── redis (Railway plugin)        ← ~$3/mo
總計：約 USD 17-25/月，含 $5 已用抵額
```

**Monorepo vs 多 Repo**：**強烈建議 Monorepo**。理由：
- Claude Code 在單一倉庫內可同時讀取前後端，refactor 時能跨端改型別。
- Railway 支援同一 GitHub repo 內以 root directory 區分多服務（`apps/web`、`apps/api`）。
- 用 pnpm workspaces 或單純的兩個資料夾即可，**不需** Nx / Turborepo 等重量級工具（20 人系統用不到 build caching）。

```
clinic/
├── apps/
│   ├── web/        # Next.js（Railway service: frontend）
```

**身份證 AES 加密實作要點（個資法合規）**：
- 用 envelope encryption：DB 存 AES-GCM ciphertext + nonce，加密 key 存 Railway 環境變數 `ID_ENCRYPTION_KEY`。
- 同一身份證字號每次加密產生不同 ciphertext（GCM 有 nonce），所以**無法用 ciphertext 做查詢**——若需查詢，另存一欄 HMAC-SHA256（同一明文 → 同一 HMAC，可建索引、但不可逆推）。
- 切勿用 ECB 或 CBC 無 MAC 模式。

**PDF 中文字體**：WeasyPrint 走 `@font-face` 載入 Noto Sans CJK 即可，不需在程式裡註冊字體（這是 ReportLab 的痛點）。

## 8. 三維資料結構：空間預約表設計

**推薦：單表設計 + tstzrange + EXCLUDE GIST 約束**

依 PostgreSQL 官方文件（postgresql.org/docs/current/ddl-constraints.html）：「Exclusion constraints ensure that if any two rows are compared on the specified columns or expressions using the specified operators, at least one of these operator comparisons will return false or null.」配合 Range Types 文件給出的範例：

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;

CREATE TABLE appointment (
    id              BIGSERIAL PRIMARY KEY,
    room_id         INTEGER NOT NULL REFERENCES room(id),
    therapist_id    INTEGER NOT NULL REFERENCES therapist(id),
    client_id       INTEGER NOT NULL REFERENCES client(id),
    time_range      TSTZRANGE NOT NULL,  -- [start, end)
    status          TEXT NOT NULL CHECK (status IN ('booked','executed','cancelled','no_show')),
    locked_at       TIMESTAMPTZ,         -- 核銷後鎖定
    created_at      TIMESTAMPTZ DEFAULT now(),
    -- 空間時段不可重疊（已取消的不算）
    EXCLUDE USING gist (
        room_id WITH =,
        time_range WITH &&
    ) WHERE (status NOT IN ('cancelled'))
);

CREATE INDEX idx_appt_therapist_time ON appointment USING gist (therapist_id, time_range);
CREATE INDEX idx_appt_date ON appointment ((lower(time_range)::date));
```

若部署目標已能用 PostgreSQL 18（Railway 是否支援需自行確認），可改用更清晰的 `PRIMARY KEY (room_id, time_range WITHOUT OVERLAPS)` 語法，行為等價於上方 EXCLUDE，但語意更直觀。在 PG 18 之前一律用 EXCLUDE GIST。

**為什麼不要拆成「日期 × 時段 × 空間」三維表**？
- 三維展開後資料量爆炸（假設一年 365 天 × 每天 20 個時段 × 10 間空間 = 73,000 筆「空白格」），且日曆 UI 並不需要這種展開——FullCalendar 只要傳「已預約事件」。
- 用 `tstzrange` 直接表達「2026-05-12 14:00 至 15:00」一筆即可。需要算「空檔」時用 SQL `tstzrange '[09:00, 18:00)' - 已預約 ranges`，效能極好。
- 跨年完全不用特別處理（`tstzrange` 本身就是時間區間）。

**衝突檢查效能**：EXCLUDE 約束底層用 GiST index，O(log n) 範圍重疊查詢。20 人診所一天頂多 200 筆預約、一年 50,000 筆，GiST 完全游刃有餘。

**前端日曆資料拉取策略**：
- 用 FullCalendar 的 `events` callback，每次切換 view 時呼叫 `GET /appointments?start={ISO}&end={ISO}&room_id={}` 拉該區間資料。
- 後端用 `WHERE time_range && tstzrange($1, $2)` 一個查詢搞定。
- 不需要 WebSocket 即時更新（10 人在線、低頻操作），用「預約後 invalidate query cache」就夠（搭配 TanStack Query）。

**官方文件連結**：
- PostgreSQL Range Types: https://www.postgresql.org/docs/current/rangetypes.html
- EXCLUDE Constraint: https://www.postgresql.org/docs/current/ddl-constraints.html
- FullCalendar Resource View: https://fullcalendar.io/docs/resources

## 9. 帳務不可變性實作

**推薦：標準 audit table + 應用層鎖定，不採完整 Event Sourcing**

```sql
-- 流水帳主表（mutable until locked）
CREATE TABLE ledger_entry (
    id              BIGSERIAL PRIMARY KEY,
    appointment_id  BIGINT REFERENCES appointment(id),
    amount          NUMERIC(10,2) NOT NULL,
    status          TEXT NOT NULL,  -- pending, reconciled, voided
    locked_at       TIMESTAMPTZ,    -- 一旦填入即不可改
    ...
);

-- Audit log（append-only，所有變更皆寫入）
CREATE TABLE ledger_entry_audit (
    audit_id        BIGSERIAL PRIMARY KEY,
    ledger_entry_id BIGINT NOT NULL,
    operation       TEXT NOT NULL,    -- INSERT / UPDATE / DELETE
    changed_by      INTEGER NOT NULL, -- user_id
    changed_at      TIMESTAMPTZ DEFAULT now(),
    before_data     JSONB,
    after_data      JSONB
);

-- Trigger：所有 INSERT/UPDATE/DELETE 自動寫 audit
CREATE OR REPLACE FUNCTION audit_ledger() RETURNS TRIGGER AS $$
BEGIN
    -- 鎖定後禁止 UPDATE
    IF TG_OP = 'UPDATE' AND OLD.locked_at IS NOT NULL THEN
        RAISE EXCEPTION 'Ledger entry % is locked', OLD.id;
    END IF;
    INSERT INTO ledger_entry_audit(...) VALUES (...);
    RETURN COALESCE(NEW, OLD);
END;
$$ LANGUAGE plpgsql;
```

**為什麼不用完整 Event Sourcing？**
- ES 強項是「複雜業務領域、需 replay 重建狀態」——本案帳務領域夠單純，每次都重 replay 反而慢。
- ES 需學專屬框架（如 eventsourcing 套件）、需設計 aggregate / event store / snapshot，對 Claude Code 與後續維護者心智負擔大。
- 標準 audit table 模式 LLM 與所有後端工程師都熟，問題排查直觀（直接 SQL 查 audit 表）。

**PostgreSQL Row-Level Security 是否適用？**
- **不建議在本案啟用 RLS**。RLS 適合：「同一 DB 連線、不同使用者直接查詢的多租戶系統」。本案是「應用層先驗證 → FastAPI 用一個 DB role 連線」，RLS 反而要把 user_id 傳入 session variable，繞一圈又繞回應用層判斷。
- 但建議啟用 **pgAudit 擴充**（若 Railway 環境支援）作為合規證據：DB-level 完整記錄所有 SELECT/UPDATE，當未來有稽核需求可直接出示。

**帳務鎖定守衛建議**（雙保險）：
1. **DB 層**：上面的 trigger 阻擋 `locked_at IS NOT NULL` 後的 UPDATE。
2. **應用層**：SQLAlchemy model 加 `@validates` 檢查 + service layer 顯式 `if entry.locked_at: raise LockedError`。

**官方文件連結**：
- pgAudit: https://www.pgaudit.org/
- SQLAlchemy Events: https://docs.sqlalchemy.org/en/20/orm/events.html

## 10. 風險與替代方案

### 10.1 若 Railway 出問題的遷移成本評估

| 目標平台 | 遷移難度 | 主要差異 | 月費（同等規模） |
|---------|---------|---------|---------------|
| **Fly.io** | 低 | Dockerfile 即可、Postgres 自管略複雜 | USD 15–25 |
| **Render** | 低 | 類似 Railway，PG 較貴 | USD 25–35 |
| **DigitalOcean App Platform** | 中 | YAML 設定、PG managed 額外費 | USD 30–40 |
| 自架 VPS（Hetzner CX22 + Coolify） | 高 | 要會 Docker compose、SSL、備份 | USD 5–8（但時間成本高） |

**降低 lock-in 的具體做法**：
- 用 Dockerfile 部署（而非 Nixpacks 黑魔法），讓 image 可移植。
- 環境變數標準化（`DATABASE_URL`、`REDIS_URL`），不依賴 Railway 專屬 `RAILWAY_*` 變數。
- DB 備份每週手動下載一份到本地 / Backblaze B2。

### 10.2 自建 vs Supabase 取代部分後端

**結論：不建議**。Supabase 適合：
- Realtime 需求重（chat、看板協作）
- 不想寫後端（純 frontend + DB API）
- 已是 Supabase 生態

本案需要「狀態機驅動的複雜業務邏輯 + 排程 + AES 加密 + 多層權限」，這些都繞不開後端服務。把 DB 放 Supabase、後端放 Railway 會造成：(a) 跨網路 query latency；(b) 兩個 dashboard 與帳單；(c) Supabase Auth 與你自建的 RBAC 重疊衝突。

### 10.3 台灣個資法技術面要點

依據個人資料保護法第 27 條與「醫療法」、「醫療法施行細則」相關規定，醫療機構處理病人病歷與身份識別資料須具「適當之安全維護措施」。技術上至少做到：

1. **身份證字號加密儲存**（AES-256-GCM，envelope encryption）。實務上法院已將「AES-256 加密」視為合規防護的具體指標（依 iThome 報導之「飯店個資外洩案」，業者雖提交「個人資料 AES256 加密機制截圖」等證據，仍須證明事前已有妥善管理；換言之，AES-256 加密是必要但非充分條件）。
2. **完整 audit log**（誰、何時、改了什麼），保留至少 5 年。
3. **角色分權**（最小權限原則）：心理師只能看自己個案、不可看財務；行政可看預約但不可看病歷內容。
4. **傳輸加密**：Railway 提供的 domain 自帶 TLS；自訂網域用 Let's Encrypt 自動續簽。
5. **登入限速 + 失敗鎖定**：對 `/login` 加 rate limit（5 次/分鐘）+ 連續失敗鎖帳號 15 分鐘。
6. **密碼策略**：argon2 雜湊 + 強制 12 位以上 + 定期更換（依診所政策）。
7. **資料外洩通報機制**：依個資法第 12 條，發現外洩應「以適當方式」通知當事人。建議在 audit log 上層加 anomaly detection（同一帳號異常時間登入、大量下載個案資料時自動 Slack 警報）。
8. **個資刪除請求**：規劃軟刪除 + 真實刪除 SOP（半年後清除）。
9. **資料庫備份加密儲存**，且備份檔同樣納入 audit。
10. **特種個資特別處理**：依個資法第 6 條，**病歷、醫療、基因、性生活、健康檢查、犯罪前科**屬「特種個人資料」，原則上不得蒐集處理利用，例外情形需符合法定要件且有「適當安全維護措施」。診療紀錄、診斷碼必為特種個資；應在 schema 設計時即明確標註欄位敏感度，並對特種個資欄位的存取另寫獨立 audit trail。
11. **委外處理（如 Railway 為境外雲）需注意**：個資法第 21 條規定國際傳輸個資若無中央目的事業主管機關特別限制即可，但建議在「隱私權政策」中明確告知病人「資料儲存於美國地區 AWS（Railway 底層）」。

**Railway 機房位置**：目前主要 US-West（Oregon）與 EU-West，**沒有亞太節點**。若診所對「資料須留台灣」有嚴格要求（例如未來接健保署服務），需考慮：
- 升級到 Railway Pro 後 + Metal 方案選擇地區
- 改用 GCP Taiwan region（自架 GKE）或本地 IDC（中華電信 HiCloud）

對 20 人診所、純內部營運系統，US-West Railway + TLS + 加密 + audit 已屬合理工程實踐。
