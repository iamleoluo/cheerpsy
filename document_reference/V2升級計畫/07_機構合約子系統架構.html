核心主張：主系統不需要知道「為什麼是這個價格」，只需要知道「答案是什麼」。 子系統是一台報價與額度引擎——主系統問一次、拿到一份完整自足的答案（Quote），把它原封不動存成快照，之後所有帳務、報表、收據都只讀這份快照，永遠不再回頭重算。這一個決定，就讓 54 個方案的變異全部關在子系統裡。

這句話同時透露兩件事：① 拆方案的動機是額度要分開算，不是價格；② 拆開之後核銷還是要合併。所以正確的模型是 方案 ≠ 額度池 ≠ 核銷群組，三者基數不同，必須拆成三個概念（見 §4）。

1.5 收據：一次服務可能要開兩張，名目來源不同

  • 分開開立（回覆已定案，不合併成一張）：個案自付額收據給個案、機構收據給機構。
  • 名目來源不同：自費／個案自付額的名目以諮商項目為主（心理治療／心理諮商／會面交往／摘要報告）；機構收據名目以方案設定為主（諮商鐘點費／心理諮詢鐘點費／場地費／行政規費）。
  • 多數機構不用開收據：清冊中大量「不用開立收據」。回覆更正了原本的理解——衛生局市民、15-45青壯、國軍都不用開給機構，只有台南教支才有雙收據情形。
  • 臨時改收款對象：蛹之生 EAP「如果律師臨時請假或個人原因產生額外費用，會改由向律師請款，另開收據項目為 *月EAP場地費」，並希望「另外跳出視窗填寫該請款單位名稱」。
    注意這與第①組定稿裡「場地租借未到 → 付款方改為借用人自付」是同一個模式：付款方可在單筆交易上被改寫。應設計成通用能力，而非兩處各寫一次。

1.6 兩個我在清冊裡發現、目前架構完全沒有位置的欄位

缺漏 1個案代號

清冊有一欄「個案代號 #每位個案代號不同」，16 個方案標記為「有」：警局轉介、警局、台南教支、教支單次諮詢、教支中心、人事處系列 7 個局處、家防中心、家防相對人、北家扶、南家扶。

這是機構端配發給該個案的編號，核銷時要對得上。現行 cases 與 case_institution_quotas 都沒有這個欄位——這代表目前只能寫在備註裡，核銷時要人工比對。應該放在「個案機構狀態（enrollment）」上，因為同一個案在不同方案會有不同代號。

收穫行政／心理師確認清單

54 個方案全部都有「行政確認清單」與「心理師確認清單」兩欄，內容是逐項的 □ 勾選清單。例：台南教支的行政清單是「□ 檢核教師證／□ 心理師填寫簽到表／□ 填寫諮商轉介摘要表／□ 個案第六次填寫滿意度調查表」。

這正是第①組定稿裡「行政流程提醒」的資料來源。我在 01 曾把「方案主檔資料尚未提供」列為 R3 風險（當時提醒清單是寫死示範）——這份清冊把它補齊了，R3 可以解除。
另有第三欄「核銷準備資料」是核銷案層級的文件清單（領據／月次清冊表／匯款帳戶影本⋯），與前兩者不同層級，不要混在一起。

結論右欄（不需要知道的事）全部是變異的來源，而左欄（非知道不可的事）形狀完全固定——不管是 54 個方案還是 154 個方案，主系統要的永遠是同一組：幾個金額、幾個字串、一個布林、一個列舉。
這就是邊界。子系統負責把變異算成這組固定答案；主系統只存答案。

2.1 關鍵機制：報價快照（Decision Snapshot）

主系統向子系統要一次「報價」，拿到一份完整自足的答案，原封不動存在自己的紀錄上。之後所有帳務、報表、收據都只讀這份快照，永遠不回頭重算。

// 預約當下
POST /appointments
  └─ 子系統.quote(case, plan, 型態, 日期, 時長, 地點) → Quote
  └─ appointments.plan_quote = Quote            // JSONB 快照，原封不動
  └─ appointments.case_payable = 400            // 攤平出來供 SUM 用
  └─ appointments.institution_payable = 1600
  └─ 子系統.reserve(appointment_id, quote_id)   // 同一交易內扣額度

// 三個月後查月報表：不再呼叫子系統，直接讀快照
SELECT SUM(case_payable), SUM(institution_payable) FROM session_records ...
✅ 合約改價不會污染歷史

明年 15-45青壯 從 $1600 調成 $1700，去年的紀錄仍是 $1600——因為存的是當時的答案，不是指向規則的外鍵。這對核銷稽核是硬需求。

✅ 報表不依賴子系統可用性

月報表、日結、收據全部只讀主系統自己的欄位。子系統就算掛了、改版了、被抽換成別的實作，歷史報表數字不變。

✅ 新方案不動主系統 schema

Quote 的形狀固定。新增一個奇怪的方案 = 在子系統加一列規則資料，主系統一行程式都不用改。

代價（要誠實說）① 資料有重複：同一筆價格同時存在子系統規則與主系統快照裡。這是刻意的，換來的是稽核可追溯與去耦合。
② 改錯要走更正流程：如果報價當下就填錯（例如心理師選錯方案），不能靠「改規則」修正歷史，必須明確地作廢重開該筆。這其實符合定稿一貫的立場：「錯誤應該被看見，而不是被掩蓋」。

3子系統的形態與依賴方向

已定案（2026/09/07）採模組化單體：同一個 FastAPI app、共用同一個資料庫，子系統是一個獨立的 package。不做獨立服務、不多開容器。

3.1 你問的那題：誰是 package、誰去調取？

你提出「或是反過來，把主系統寫成 package，然後讓子系統調取」——這個直覺是對的，而且比我原本的提案更好。但它需要補上一塊才完整。以下把三種可能攤開看。

方案程式碼依賴方向問題
(a) 主 → 子
我原本的提案		主系統 import 子系統的 facade可行但不理想主系統的程式碼裡會出現「機構」這個詞。每個碰錢的地方都長出 if 機構案: 分支。而且子系統要讀 cases／session_records 時會變成循環依賴
(b) 子 → 主
你的直覺		子系統 import 主系統的 models方向對，但不完整子系統讀資料很順，但預約當下主系統要跟誰要價格？如果主系統不能 import 子系統，就必須有人把實作「送進來」
(c) 依賴反轉
建議		程式碼只有一個方向：子 → 主
呼叫方向：主 → 子（透過介面）		就是 (b) 補上那一塊之後的完整形態

3.2 (c) 具體長什麼樣

主系統定義介面（它需要什麼），子系統實作介面（它怎麼算出來），啟動時把實作註冊進去。主系統從頭到尾沒有 import 過子系統任何一行。

① 主系統沒有「機構」這個詞

它只知道「這場諮商可能有一個外部給付方」。介面刻意命名為 FundingPlanProvider 而不是 InstitutionProvider——因為哪天出現保險給付、企業方案、新的政府計畫，那是再寫一個 adapter，主系統不動。

② 主系統可以獨立跑

不註冊任何 provider 時，list_eligible_plans 回空陣列＝純自費診所。這讓主系統可以單獨測試，也讓「主流程是否乾淨」有了可驗證的標準：把子系統整包移除，主流程要還能跑完。

③ 子系統讀資料很自由

核銷要撈 session_records、要 join cases——子系統可以直接 import、直接 join，因為依賴方向允許。不需要為了核銷再開一組 API。

3.3 目錄結構與強制隔離

apps/api/app/
├─ models/            # 主系統
├─ routers/           # 主系統 API
├─ funding/           # ★ 主系統定義的「port」——介面與 DTO 住在這
│  ├─ ports.py        #   FundingPlanProvider (Protocol)

一條 lint 規則就能守住app/institution 以外的任何檔案，禁止 import app.institution.*。
比原本的規則更單純——原本要寫「禁止，除了 facade 例外」，現在是沒有例外的禁止。用 ruff 的 flake8-tidy-imports（banned-api）或 CI 裡一行 grep 都做得到。這條規則就是「主系統保持乾淨」的技術保證。

3.4 為什麼不做獨立服務（保留紀錄）

已定案不做，但把理由記下來，日後若規模改變可重新評估：① 額度扣減必須與建立預約同一個資料庫交易——跨服務就要補償交易，而「預約建了額度沒扣」在診所現場要到月底核銷才會發現。② Windows 部署成本——目前 docker-compose.prod.yml 四個容器，且已知從 SSH 執行 docker compose build 會因 Docker Desktop 憑證綁互動式 session 而失敗，每加一個服務就多一份那個痛。③ 單一維護者。
而 (c) 的介面本來就是可序列化的 DTO，日後真要抽出去，只是把函式呼叫換成 HTTP，資料契約一個字都不用改。

4三層資料結構

你提的三層切分是對的。這一節把每一層的擁有者、欄位、與生命週期定清楚。

三層的擁有權原則 Layer 1（個案機構狀態）擁有者＝子系統，主系統不複製、只讀取顯示。
Layer 2（預約用了什麼方案）擁有者＝主系統，內容是子系統給的快照。
Layer 3（核銷案）擁有者＝子系統，主系統完全不碰，只提供 session_records 供其撈取。

4.1 Layer 1 · 個案的機構狀態列表（enrollment）

你說「目前個案本人的資料中缺少當前機構案狀態」——正確，而且這是現行 case_institution_quotas 最大的不足：它綁在 institution 而非 plan，也沒有預留/預約/使用三態。

4.3 Layer 3 · 核銷案＝容器

已定案（2026/09/07）核銷案是一個容器。容器的「收納規則」依方案而定：有的是以個案為單位、裝滿 N 次（人事處 4 次、脆家 8 次、社工支持 4 次），有的是以時間為單位（月／季／學期）。行政隨時可以先開一個空容器，系統依規則把紀錄撈進來。裝不滿也可以送出——個案做 3 次就不來了，這 3 次照樣可以核銷。

這個「容器」模型比原本設想的「門檻擋關」單純得多，而且更貼近實際作業：門檻不是阻擋條件，是容量上限。

欄位說明
inst_claim_cases（核銷案＝容器）
claim_noYYMM + 流水2碼（如 202607-01）
claim_group_key核銷群組——國軍-個別／講座／團輔 三個方案共用同一個 group，因此進同一個容器
grouping_mode容器的收納規則：per_case_count（以個案為單位，容量 N 次）／period（以時間為單位）
capacity容量。per_case_count 時為 N（4／8）；period 時為 null
period_start / period_end撈紀錄用的區間，不綁定（「時間的區間是為了撈紀錄，沒有要綁定」「送出時才會是最終的區間」）
statuscollecting → ready → submitted → received → closed；另有 voided
settlement_modeclaim_then_pay／pay_then_claim（儲值型）／pay_no_claim（先撥款不核銷後補收據）
applied_amount申請金額
received_date / received_amount收款日期與金額
income_tax_amount / transfer_fee / net_received所得稅 10%、轉帳手續費、實際入帳（回覆的範例：$27,000 − $2,700 − $30 = $24,270）
locked_at收款後即鎖定，要改需上層權限
inst_claim_lines（容器裡的明細）
session_record_idFK → 主系統 session_records
claimed_amount本筆請款金額（＝快照的 institution_payable，可回溯調整）
actual_hours / registered_hours / registered_unit_price實際時數與核銷單登記時數（台南地院 1hr→2hr×$800；台南女中／輔諮南一區 1hr→1.5hr×$1000）。轉換在建立核銷案時做，但結果要存下來

容器的行為

情境行為
行政先開空容器隨時可開。每月 1 號起有預約就能建，讓心理師可以開始上傳資料
紀錄怎麼進容器依 grouping_mode 自動撈：per_case_count 撈「該個案在此方案尚未被任何容器收納的紀錄」，滿 N 筆即標示可送出；period 撈區間內全部
裝滿狀態轉 ready（提示可送出），不強制立刻送
沒裝滿也要送允許行政 3 次就要核銷也可以。做 3 次就不來的個案，這 3 筆照樣送得出去
沒被撈進來的紀錄提醒，不阻擋送出前列出「本區間內未被收納的紀錄」，讓行政確認是「下個月才要核銷」還是「真的漏了」
跨月遺留提醒下個月建容器時，系統要提示「上個月還有 N 筆未收納」。行政可能是刻意先不撈，所以只提示不強制
「未收納紀錄」是一個具體的查詢，要做成常駐檢視 session_records 中 funding 屬機構、未被任何 inst_claim_lines 引用、且該方案仍在有效期內 的紀錄。
這個檢視同時服務三個場景：① 送出前的漏單提醒；② 下個月的跨月遺留提醒；③ 行政隨時想確認「有沒有錢忘了收」。建議做成子系統的一個常駐頁面，而不是只在送出時跳一次。

收入認列 vs 核銷送件：兩條獨立的時間軸

已定案（2026/09/07） 收入認列 ＝ 諮商實際執行的那個月，永遠不變。核銷送件是另一條時間軸，可以晚好幾個月。中間的狀態就是機構應收款（待核銷中）。
撥款進來之後，收入仍然掛在原本執行的那個月，入帳只是把應收沖掉、影響現金流，不會把收入搬到入帳月。
7月  個案做了 3 次（人事處，容器容量 4）
     └─ 收入認列：7 月 × 3 筆　　　　　// 月報表 7 月，不會變
     └─ 機構應收款：+$4,800　　　　　　// 待核銷中

8月  做第 4 次 → 容器裝滿
     └─ 收入認列：8 月 × 1 筆
     └─ 核銷案送出（含 7 月的 3 筆 + 8 月的 1 筆）

9月  機構撥款 $6,400，扣稅 $640、手續費 $30 → 實際入帳 $5,730
     └─ 收入認列：不動（7 月仍是 3 筆、8 月仍是 1 筆）
     └─ 機構應收款：−$6,400　　　　　　// 沖銷
     └─ 現金流：9 月 +$5,730
這代表主系統需要一個「機構應收」的狀態，但它不需要知道核銷細節 session_records 上機構部分的 payment_status 走 unpaid → claiming → claimed（現行已有這三個值）。子系統在容器送出時把它推到 claiming、入帳時推到 claimed。主系統的應收帳冊只讀這個欄位，完全不必知道容器、門檻、扣稅這些事。

6.4 什麼情況才需要改程式

不用改程式建資料即可
  • 新增合約／方案／費率／額度規則
  • 調價、改額度、改有效期間
  • 新的核銷時程組合（月／季／學期／門檻）
  • 新的收據名目、確認清單項目
  • 方案拆分或合併核銷群組
需要改程式新增規則「維度」
  • 出現六個條件變數以外的計價依據（例如「依個案年齡分級收費」）
  • 出現第四種撥款模式
  • 出現額度單位不是次數也不是金額（例如「時數」）

這類改動預期一年一兩次，且只動子系統內部。

8.1 借場地：只借用「核銷」，不進「額度」

你的說法是關鍵：「子系統需要管的是這個個案當前的狀態，這個預約到底是實際的場地還是什麼，其實都不用去在乎它」。這句話把子系統的職責界定得非常乾淨。

子系統的三個能力一般機構案借場地
報價（費率規則）用用（場地費率）
額度（enrollment 三態）用不用無個案、無額度概念
核銷（容器）用用要進機構應收、要開場地費收據
實作上這自然成立：核銷明細指向的是 session_records／appointments，不是 enrollment。所以一筆沒有 enrollment 的場地租借，照樣可以被容器收納、送核銷。不需要為借場地寫任何特例。

8.2 薪酬計算：一條公式，兩種金流

心理師應得 = 方案鐘點費 × 該心理師抽成率        // 兩種模式都一樣

抽成 (commission)：機構 → 慈恩 → 心理師領「應得」
  └─ 機構應收 +鐘點費　　　心理師酬勞 +應得

回扣 (kickback)：  機構 → 心理師（全額）→ 心理師回繳慈恩
  └─ 機構應收 不計　　　心理師酬勞 −(鐘點費 − 應得)
     即回繳金額 = 鐘點費 × (1 − 抽成率)
兩種模式共用同一條公式與同一個抽成率，差別只在現金流方向與帳務歸屬。這比原本設想的「逐方案談定回扣比例」單純得多——users.commission_rate ＋ 既有的 commission_rate_used 快照就夠了，不需要新的比例主檔。
外出保底（OUTPATIENT_MIN_FEE = 1000）維持現行 settlement.py 的實作不動。

8.3 流水號階段可預留、不可消耗 —— 一條必須寫死的驗證規則

你點出的這件事很重要：「流水號期間不可能產生實際的金流，因為要產生實際金流就必須要有初診」。這正好對應到額度三態的分界線。

個案階段可做什麼額度動作為什麼
流水號階段
temp_seq，未初診		媒合、booking 時間已預留→已預約
enroll() / reserve()		要先把方案額度佔住，避免被別人用掉
初診有到產生病歷號、補機構個案代號—身分確立，才有金流資格
正式個案

要寫進 consume() 的前置檢查 consume(appointment_id) 執行前必須驗證：
① 該個案已有正式病歷號（cases.case_number IS NOT NULL）——否則拒絕，並提示「請先完成初診報到」
② 若該方案 requires_external_code = true（16 個方案），enrollment 上必須已有個案代號——否則允許 consume 但標記為「待補代號」，並在核銷收納時擋下（因為核銷單一定要對得上機構的編號）
兩層檢查的嚴格度不同是刻意的：不要因為代號還沒拿到就卡住櫃檯的報到收款流程，但也不能讓沒有代號的紀錄混進核銷單。
