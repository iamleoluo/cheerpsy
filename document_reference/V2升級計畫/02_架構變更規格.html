0如何使用本文件

本文件是實作的唯一技術依據。順序是刻意設計的：先資料模型，再狀態機，再 API 契約，最後才是「畫面需要什麼資料」——因為畫面的需求必須能被前面三層滿足，反過來設計會漏掉衝突檢查、額度扣減這類跨畫面的規則。

與 03 / 04 / 05 的關係 03 操作體驗細節清單記錄「這裡要怎麼做」的視覺與互動規則，本文件不重複。04／05 操作樣本的每一個 API 呼叫，都必須能在本文件 §5 找到定義；每一個 DB 欄位變化，都必須能在 §1 找到。這是刻意的交叉檢核設計。
範圍提醒本文件只涵蓋第①組（診間日曆／預約作業／預約總表／我的今日／我的班表）需要的資料模型與 API。②③組的表結構只列到「需要哪些欄位」的程度，不展開端點細節（見 §1.3）。

1.3 ②③組表的最小可用預留（不展開細節）

依 C9 裁示：寫入端資料模型做完整，讀取端不動。以下表只列出第①組會寫入的欄位，讀取（日報表/月報表/應收帳冊的呈現邏輯）留待第②組定稿：

  • hall_bookings.fee_to_clinic_account=true 的紀錄：目前只寫入，尚無「月報表心理師當月收入」的串接

4狀態機

4.1 預約出席狀態機（appointments.check_in_status）— 全案樞紐

狀態觸發副作用
pending（待報到）建立預約時的初始值無
arrived（已到）櫃檯 / 心理師按「已到」寫入 checked_in_at/_by；若走機構額度：quota.reserved_count -1（或 booked→used，視當時是否已從 reserved 轉入 booked）；此時才建立 session_records（payment_status='unpaid'）；appointments.status 改為 'executed'
no_show（未到）櫃檯 / 心理師按「未到」→ 填原因寫入 no_show_reason/_note/_followup；不建立 session_records；額度：quota.booked→reserved還原（不是釋回，個案仍保留額度）；appointments.status 維持 'booked'（供對帳追蹤，不轉 cancelled）
與現行 materialize_due_appointments 的關係P1 後該函式停用但不刪除，改為行政手動觸發的「補登」工具（例：行政忘了幫某筆按已到，且已經過了很久）。正常流程完全由 check_in 端點驅動，不再有背景排程或懶惰執行。

4.2 額度三態流轉（case_institution_quotas）

加入方案（尚未排預約）
  reserved_count = total_count 　// 全數先預留，避免被別人用光

排一次預約（quota_id 指向此筆）
  reserved_count -= 1　// 已預約 = COUNT(booked appointments WHERE quota_id=this)，查詢時算

按「已到」
  used_count += 1　　　// 已預約 → 已使用

按「未到」或取消該筆預約
  reserved_count += 1　// 已預約 → 還原為已預留（不是釋回！個案仍保留額度）

個案結案
  total_count = used_count；reserved_count = 0　// 已預留+已預約 全數歸零（沿用 cases.py:324-333 現行寫法，僅補上 reserved 歸零）
恆等式 used_count + reserved_count + COUNT(booked) = total_count 全程成立，供稽核 SQL 定期檢查。

4.3 收款狀態（session_records.payment_status）— 沿用既有

不變：unpaid → paid（自費）／unpaid → claiming → claimed（機構）。唯一變化是建立時機：從「時間到自動建」改為「按已到才建」（見 4.1）。三步報到流程對應：

步驟UI寫入

2收款（自費需收款者才出現；月結／機構全額跳過）session_records.payment_status unpaid→paid（自費）或標記待請款（機構）；payment_method/payment_note/paid_at

4.4 媒合狀態（referrals.status，P5）

8共用帳號的 actor 傳遞設計（A8）

① 登入時

共用帳號（is_shared_account=true）登入時，前端多一個「請輸入本人姓名」欄位。後端 POST /auth/login 增加 optional actor_name 參數，寫入 JWT claim：{sub, role, name, actor_name, exp}。

② 每次寫入

get_current_user dependency 額外解析 actor_name claim，掛在 request.state。所有寫入 audit_log、appointment_admin_tasks.done_by_name、appointments.checked_in_by 對應的顯示名稱時，優先取 actor_name，否則 fallback 到 user.name。

③ 顯示

畫面顯示邏輯統一：is_shared_account ? "實習心理師（{actor_name}）" : user.name。前端只需一個共用的 displayActorName() helper。

④ 登出

JWT 過期或登出即清除，不持久化 actor_name 到 users 表 —— 每次登入都要重新填寫（定稿 Q3 明確要求）。

此設計不解決「異動紀錄無法從系統層面證明是誰做的」這個根本限制（診療所已知悉並接受，見 01 §丙4）。人數變多時的升級路徑：把該心理師的 is_shared_account 設回 false、另開一般帳號即可，資料表結構不需異動。
