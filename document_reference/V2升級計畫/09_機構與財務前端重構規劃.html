1為什麼機構與財務不能照樣本做

1.1 機構：原型假設「一個方案一個價」，實際是「有序的費率規則」

原型的機構資料模型只有這樣一行（v7 第 2538 行）：

const INST = {
  "衛生局 / 15-45青壯":{quota:3, self:400, inst:1600},
  "衛生局 / 脆家方案" :{quota:6, self:0,   inst:2000},
  "國防部 / 國軍EAP"  :{quota:6, self:0,   inst:1800},
  "教育局 / 教支"     :{quota:4, self:0,   inst:1800}
};

一個方案 ＝ 一個額度上限 ＋ 一個自付額 ＋ 一個機構請款額。但《260831新版-機構合約方案清冊》裡的實際規則沒有一個是這樣：

實際方案實際計價規則原型能表達嗎
衛生局 15-45 青壯依次數分級：第 1 次 $1,600／自付 $0；第 2 次起 $1,400／自付 $200不能
國軍 EAP金額池：方案層級總額 $149,000，扣的是錢不是次數不能
聊心茶室回饋制：心理師自收，診所收回饋金——不是抽成不能
鉅微（借場地）不佔額度、只收場地費，酬勞模式又不同不能
容愛協會年度上限之外還有每月 4 次的週期性子上限不能
警局／奇美家照6+3：基本 6 次，可申請延長 3 次不能

後端（07 §1、已實作）用的是有序費率規則：inst_rate_rules 一張表，每條規則帶一個 when_json 條件（次數區間／諮商類型／心理師），由上往下先匹配先贏，命中後給出 unit_price 與 case_payable。這是原型 UI 完全沒有的東西——費率規則編輯器是一塊全新的畫面，不是把舊表格改欄位就好。

1.2 機構：原型缺「酬勞模式」這個維度

後端 inst_plans.compensation_mode 有三種值，原型與樣板都只認得第一種：

commission 抽成

診所收全額，依心理師抽成率拆分。這是原型唯一認得的模式。

kickback 回饋

心理師自收費用，回饋一部分給診所。金流方向相反，日報表的「已收現金」不能算進來。

therapist_rate 心理師定價

單價由心理師個人費率決定，不是方案決定。報價時要帶心理師 id 進去。

影響範圍比看起來大這一欄同時影響：機構方案編輯畫面（要能選）、預約報價（要帶心理師）、日報表（回饋制不計入診所現金收入）、心理師「我的酬勞」（三種算式）、以及月結酬勞計算。這是財務也要一起重構的根本原因之一。

1.3 機構：核銷案的分組方式不只「期間制」

原型的核銷案固定是「選機構 → 選期間 → 選人 → 建立」，也就是期間制。但後端 inst_claim_cases.grouping_mode 有兩種：

  • period 期間制：某機構某方案在 7/01–7/31 之間的紀錄整批請款。原型有的就是這種。
  • per_case_count 次數制：某個案每滿 N 次請一次，與月份無關。原型完全沒有這個概念，但實際清冊裡有這種方案。

另外後端的容器是可以裝不滿就送出的（07 §4.3 你的裁示：核銷案是彈性容器，不是硬性門檻），原型則寫死「資料齊備才能轉待送出」。這兩件事的 UI 呈現完全不同。

定案（§7.1 已裁示）依付款方切開——但「付款方」不是「這張預約的 funding_source」，而是每一筆錢自己的付款方：

1.4a ★ 補充裁示：機構案的自付額必須併入「每日該收」，不能只在機構頁面才看得到

你的裁示，逐字記錄「機構案有時候會需要自費款。例如一筆 1600 元的款項，可能有 400 元是個案要自付，剩下 1200 元是機構補助。那這 400 元自費款也要納入整個自費流程，一般來說當日就要結清……不管付款方式是日結還是月結，都屬於自費流程」「自費部分：在櫃檯當下就要看到……如果上個月的月結還沒結清，行政在報到或開收據當下就必須看得到」「機構案部分：基本上是行政人員點開特定頁面才需要看到」。

這決定了整個財務前端的分界，不是「機構頁 vs 財務頁」兩塊各自獨立，而是一筆機構預約的兩段金流各自併入不同的日常節奏：

自付款流程（case_payable）— 每天都要看到

不論這筆預約的 funding_source 是 self_pay 還是 institution，只要有個案自己要付的錢，一律出現在日常收款動線：診間日曆報到收款步驟、日報表流水帳、應收帳冊「未收」／「月結」分頁。上月月結未清，個案這次來報到／開收據時當場就要跳出來，不是等行政自己想到去查。

機構請款流程（institution_payable）— 主動點開才看到

只有機構要補的那一段錢（$1,200），走合約專頁的「核銷」分頁，行政主動點開合約才處理，不會也不該出現在每天的收款清單裡——這不是行政每天的例行工作。

這是一個真正的後端缺口，不只是前端分頁問題目前 /ledger 的「未收」查詢（routers/ledger.py 約 248 行）過濾條件是 payment_status=='unpaid' AND funding_source=='self_pay'——機構案的 case_payable 完全被排除在外，因為機構案走的是 copay_collected_at（08 §5.4 新欄位），不是 payment_status。這表示現在系統裡沒有任何一個查詢會把機構案的自付額顯示成「未收」。這條要在 §5 補一個明確的後端項目：一個不分 funding_source、只認「有沒有自付額待收」的統一查詢，日報表／應收帳冊／報到收款頁全部共用同一個來源，別各自兜一套邏輯出來。

1.6 財務：「我的酬勞」的算式在新模式下不成立

原型的酬勞明細是固定五欄：場次金額 × 抽成率 ＋ 外出保底 = 我的酬勞。在 compensation_mode 之下：

  • commission：維持原算式（診所收 → 拆給心理師）。
  • kickback：心理師先收到全額，欠診所回饋金。這一列在「我的酬勞」裡是負的或應該獨立一區呈現，混在同一張表會讓心理師誤讀。
  • therapist_rate：單價來自心理師個人費率，「抽成率」這一欄意義不同。

另外督導模式 A／B（users.supervision_fee_mode，P0 已加欄位）也會產生第四種金流。這頁需要的是分區呈現，不是加一欄。

3機構：分層架構與合約面板

兩個已定案的前提 ① 一頁的單位是「合約」，不是機構、也不是方案——一份合約 ＝ 與某機構的一段合作關係，底下的多個方案包在裡面，因為額度可能要整體計算。
② 首批只做 5 份合約的專屬面板，其餘走通用版，由行政以較手動的方式操作；等作業方式摸清楚後再逐一升級。

幸運的是 ①不用改 schema：inst_quota_pools.contract_id 本來就掛在合約層級，同一份合約底下多個方案天生共用同一個額度池（國軍 $149,000 就是這樣建的）。要改的只有 UI 的單位。

這一層要解決的問題54 份合約的規則差異太大，寫成一套「什麼都能表達」的通用設定檔，最後會變成一個小型程式語言——設定比寫程式還難。反過來，把原語做紮實，每份合約只寫一層薄薄的組裝碼，才是可維護的作法。Layer 3 的每個模組應該只有組裝與查詢，不含業務規則本身。

3.2 關鍵設計：讀是專屬的，寫是共用的

這是讓「每份合約各有一個量身打造的畫面」不會演變成 54 份重複程式碼的關鍵切法。

讀 — 每份合約不同

GET /institution/contracts/{id}/panel 一次回傳該面板需要的全部資料，形狀由該合約的 Layer 3 模組決定，各自有自己的 Pydantic schema。

衛生局回的是「每人額度三態 ＋ 本期待核銷名單」；國軍回的是「池子消耗 ＋ 各個案累計金額 ＋ 剩餘可用」。形狀完全不同，這是刻意的。

寫 — 所有合約共用

加入方案、報價、reserve、報到 consume、開核銷案、收納、送出、入帳、文件提交、行政核對——這些動作不管哪個機構都一樣，只是參數不同。

就是已經寫好並有測試覆蓋的那組 API（08 §2.3），一支都不用改。

為什麼這個切法重要前端只需要做兩件事：把 read model 渲染出來、按鈕呼叫共用的 write API。它不需要理解任何機構規則——規則在 Layer 3 已經算完了。這讓每份合約的面板可以獨立、快速地生出來，而且不會因為前端寫錯而算錯額度或金額。N 個 read model，1 組 write API。

3.3 首批 5 份合約 — 依模式空間覆蓋率挑選

挑選標準不是規模大小，是能不能把模式空間蓋滿。這 5 份做完，架構就被五種結構性不同的規則驗證過。

3.4 通用版 vs 專屬版：工具式 vs 導引式

兩者的差別不是「陽春 vs 完整」，而是系統要不要替行政做判斷：

通用版 — 工具式

系統不猜你要幹嘛。行政自己挑人、自己開核銷案、自己填金額、自己決定期間。畫面是一組工具。

好處：任何形狀的合約都能用，不會因為規則沒被建模就卡住。

專屬版 — 導引式

系統主動說「這 3 個人已達 4 次，該開核銷了」「池子剩 $12,000，約剩 6 次」。畫面是一條動線。

好處：把重複判斷交給系統，行政只需要確認與執行。

升級路徑：通用版是起點，專屬版是升級新合約一律先掛通用版跑著，等實際作業方式摸清楚了（也就是「比較清楚的新樣本出來」），再補一個 Layer 3 模組把它升級成專屬版。升級不用搬資料——底層一直都跑在同一套原語上，變的只有讀取與呈現方式。這也表示第一天就能上線 54 份合約，不必等 54 個面板做完。

3.6 兩條紀律

紀律一：合約模組不准直接寫 DBLayer 3 只能組裝 Layer 2 的原語。如果某份合約需要原語做不到的事，那是「該擴充原語」的訊號，不是在模組裡硬寫一段 SQL。這條守住，Layer 2 才會越用越紮實、每多做一份合約整體就更強一點；守不住，三個月後 contracts/ 會變成邏輯垃圾場，業務規則散落各處且無法測試。
紀律二：面板的候選名單，必須跟寫入端用同一個函式算「已達 4 次待核銷」這份名單，要由核銷收納時所用的同一個查詢函式產生。否則會出現「面板說可以、按下去被拒絕」——這種不一致在財務作業上特別傷，行政會開始不信任系統。

6建議實作順序

  1. 先做「照樣本」那 11 頁的骨架（App Shell ＋ 導覽 ＋ 診間日曆 ＋ 預約作業 ＋ 報到三步驟）。後端已 100% 就緒（08 §5），這段是純接線，做完就有一個能實際操作的系統，也能讓診療所提早試用回饋。
  2. 補齊 Layer 2 原語：統一自付款查詢（§1.4a，優先做，日報表/應收帳冊都靠它）、額度池扣減、週期子上限、延長流程、待核銷候選查詢、文件雙閘門移植、核銷案作廢、機構未到補助欄位。這一步決定後面每份合約好不好寫——原語越紮實，Layer 3 越薄。
  3. Layer 3 骨架 ＋ 通用版：ContractModule 基底、generic.py、GET /contracts/{id}/panel 分派。做完這步，54 份合約全部可用（通用面板），不必等專屬面板做完才能上線。
  4. 合約面板骨架 ＋ 通用面板前端：清單頁 ＋ 四分頁骨架 ＋ 共用區塊庫（三態長條、核銷清單、文件閘門、費率表）。
  5. 逐一做 5 份專屬合約，順序建議：衛生局（最典型）→ 國軍（驗證池型）→ 家防中心（驗證次數制核銷）→ 聊心茶室（驗證回饋制金流）→ 鉅微（最簡單，收尾）。每做完一份就檢查一次紀律一：有沒有東西該往 Layer 2 沉？
  6. 核銷案總表 ＋ 心理師端文件確認。機構這條線的收尾。
  7. 日報表第一期（唯讀）＋ 應收帳冊三分頁。用既有資料先讓財務看得到數字。
  8. 日報表第二期（對帳鎖定／優待／作廢／拆帳／商品）。要先補後端，且與②組定稿相依，建議等診療所財務定稿。
  9. 我的酬勞分區改版。相依於優待與 compensation_mode 都確定之後。
為什麼把「照樣本」那 11 頁排在最前面不是因為它簡單，而是因為它零阻塞——後端全好、設計全定、不等任何裁示。機構與財務原本有 3 個決策待定，這輪你已經裁示了核銷合併方式與失約費（§1.4/§1.4a/1.5），現在只剩收據編號格式卡在診療所（01 §C4）。
第 3 步是這份計畫的關鍵轉折通用版一做完，機構這塊就不再是「全有或全無」——54 份合約立刻都能用，之後每寫一個 Layer 3 模組就升級一份，隨時可以停在任何進度而系統仍然完整可用。這是「先做 5 個」這個決定能成立的技術前提。

7裁示狀態

唯一還開著的決策：收據編號格式目前 R{YYYYMMDD}{seq:04d}，原型與你的原稿是 A20260801C021-1（館別＋日期＋流水號＋分類＋檢核碼）。01 §C4 已標記這件要拉回去跟診療所談，包含「重印 vs 重開」的判定規則。日報表與收據頁在格式定案前先用現行格式，之後只需改編號產生器，不影響資料結構。

擴充方式分層：Layer 2 原語做紮實，每份新合約只寫一層薄的 Layer 3 組裝碼 ＋ 一個為它設計的前端面板
前後端介面讀專屬、寫共用：N 個 read model，1 組 write API
核銷機制合併依錢的付款方切，不依案件種類切：機構請款流程走新 inst_claim_cases；自付款流程（不分自費案或機構案的自付額）走舊 claim_batches，正名「自費結帳批次」。一筆機構預約的兩段錢各走各的（§1.4／§1.4a）
自付款的每日可見性機構案的 case_payable 必須併入日常收款動線（報到收款、日報表、應收帳冊），不能只在機構頁面才看得到；機構請款那段（institution_payable）則相反，只在合約專頁主動點開才處理（§1.4a）
失約費自費與大部分機構一律不做；個別機構方案可設定補助未到，補助金額直接進機構核銷、不消耗個人額度。不做原型那套三級費率表（§1.5）
日報表第一期先做「大概版」：KPI＋流水帳＋應收/已收切換，且必須整合統一自付款查詢。優待／拆帳／作廢／對帳鎖定全部暫緩，等②組財務定稿（§4.1）
