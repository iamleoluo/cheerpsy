5.3 P1 出席驅動：PUT /appointments/{id}/check-in

接著往下做的下一步——把 §5.1 剛接上的 consume()/release() 從「背景排程觸發」換成「使用者按出來的」。這是 01 §A1 描述的全案最大單一改動，這輪把骨架做完並測試覆蓋，「收款」「開立收據」兩步（涉及 fee_items/receipts 表）還沒做。

按「已到」

立刻建立 session_record（呼叫 settlement.build_session_record()——從 materialize_due_appointments() 抽出來的共用函式，兩個呼叫端不會各自長出不同邏輯）、plan_id 有值就呼叫 consume()、appt.status→executed。

按「未到」

寫入 no_show_reason/note/followup；appt.status 維持 booked（不轉 cancelled，供對帳追蹤，01 §C3）；plan_id 有值就呼叫 release()——已預約還原為已預留，不是釋回。

關鍵修正：materialize 必須排除已人工處理過的預約

這是這輪重構真正要修的 bug如果 materialize_due_appointments() 的查詢條件沒有加上 check_in_status == 'pending'，被人工標記「未到」的預約（status 仍是 booked）時間一過，會被這支函式誤判成「沒人管、自動結算」，生出一筆不該存在的 session_record。已加上這個過濾條件，並用兩支測試直接鎖住這個情境（見下表）。

5.4 報到三步驟後兩步：收款、開立收據

緊接著把報到流程的剩下兩步做完——POST /appointments/{id}/payment-step 與 POST /appointments/{id}/receipt。到這裡「報到→收款→開據，一頁完成」在後端已經是完整的三個端點，同一個 appointment_id 串起來。

關鍵設計決定：新開一組 copay 欄位，不動既有 payment_statussession_records.payment_status 對機構案的語意是「機構請款進度」（unpaid→claiming→claimed，核銷案容器會動它）；「櫃檯今天有沒有收到個案自付額」是另一件事。硬共用會撞語意、可能弄壞既有核銷案流程。所以新增 copay_collected_at/copay_payment_method/copay_payment_note 三個獨立欄位。只有純自費案（無機構那份）才會同步既有 payment_status——因為那條路徑本來就是乾淨的 unpaid→paid 二態，同步不會撞到任何東西，反而讓既有 /ledger 頁面能正確顯示。

收款（payment-step）

應收金額 = case_payable（有值就用它）否則整筆 amount。機構那份 institution_payable 完全不動，走既有 /ledger + 核銷案容器流程。case_payable=0（機構全額）→ 擋下並說明「免收」。

開立收據（receipt）

新表 receipts，收款項目來自新表 fee_items（8 個定稿預設值 + 自訂名稱）。收據編號沿用既有 R{YYYYMMDD}{seq:04d} 慣例——格式本身待 01 §C4 定案，先求系統內部一致。

5.5 房間衝突 DB 層防護：EXCLUDE USING GIST

01 §C5 定案「同一診間同時段不可重複預約，由資料庫層強制（非僅前端檢查）」，但 _check_room_conflict()（routers/appointments.py）從來只是應用層 SELECT-then-INSERT，兩個併發請求可以同時通過檢查、都插入成功。這輪把這個一直跳過的 §6 缺口補上。

Migration aa5a2b3c4d5f5

啟用 btree_gist extension（room_id 是純量整數，靠它才能參與 GIST 索引的等值比較）；ADD CONSTRAINT excl_room_time_overlap EXCLUDE USING GIST (room_id WITH =, time_range WITH &&) WHERE (status != 'cancelled' AND room_id IS NOT NULL)——條件與 _check_room_conflict() 的 SQL 完全一致。升級前用 DO block 先掃一次既有資料，若已有重疊直接 fail-fast 並印出衝突的 appointment id，不靜默建出一個實際上永遠會失敗的壞約束。

應用層轉譯：_flush_with_conflict_guard(db)

薄封裝 db.flush()，捕捉 excl_room_time_overlap 觸發的 IntegrityError，回滾後轉成跟 _check_room_conflict() 一樣的 409，而不是讓 Postgres 一大串原始 SQL 例外洩漏到 API 回應。已接進三個寫入路徑：create_appointment()、create_batch() 迴圈、update_appointment()（改時間/診間時）。

應用層 SELECT 檢查（快、訊息清楚）與 DB 層約束（真正的防線）疊加：正常操作走前者就會被擋下並看到人話訊息；只有兩個請求真的在同一毫秒級窗口內都通過前者檢查時，才會撞上後者，此時 _flush_with_conflict_guard 讓它一樣是乾淨的 409，不會是 500。
