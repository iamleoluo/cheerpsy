A架構級衝突 — 必須最先解決

這八項共同的特徵是：定稿要求的行為，與現行後端的基本假設相反。不是加欄位就能解決，而是要改變資料如何產生。

A1　場次成立時機：時間驅動 → 出席驅動

現況時間到就自動成立

services/settlement.py:59 的 materialize_due_appointments() 掃描所有 status=='booked' 且 upper(time_range) - 20min <= now 的預約，一律轉成 executed 並產出 session_record。機構額度也在此刻扣（:106-117）。

觸發點是讀取 ledger 時的懶惰執行（routers/ledger.py:147,199,240,264,288）—— 沒有排程器，沒人開帳冊就不會結算。

定稿按下「已到」才成立

未到 → 不產生應收，機構額度退回已預留；已到 → 額度由已預約轉已使用，該筆進當日日報表。

補充修正 3 明確推翻「起始後 30 分自動視為已到」—— 視訊與外展也必須由心理師實際按下。

衝擊面（全案最大單一改動） session_records 是整個財務鏈的上游 —— ledger → claim_batches → payouts → reports 全都建立在「它已經存在」之上。改變它的產生時機，等於改變整條鏈的觸發條件。
· 必須新增 appointment 層的出席狀態，並讓 session_record 由該狀態轉換產生。
· 現行 materialize_due_appointments 需停用（不是刪除 —— 保留為補登工具，供「行政忘了按」的例外情境）。
· 舊資料為測試資料，不需回填策略，這降低了大量風險。

A2　收款流程：事後帳冊 → 櫃台當場三步

步驟定稿要求現況對應
1 報到格子點開 → 「已到 / 未到」二選一。未到跳原因欄位（5 選 1 + 催繳方式 4 選 1）。不存在目前無 check-in 概念
2 收款已到後需收款者才長出收款區：應收金額、付款方式（現金/匯款）、優待減免、匯款末 5 碼、⏱️ 加時。routers/ledger.py:878 PUT /ledger/{id}/pay —— 但在另一個頁面、另一個時間點
3 開立收據收款完成才長出：收據編號、金額、收款項目（8 選 1 + 其他自行登打）、備註。routers/receipts.py 有 PDF 產生，但無「收款項目」主檔，且 POST 直接渲染前端送來的內容（:101,149,184），伺服器不重新驗算金額
關鍵設計要求一次只出現一步（定稿明訂）。三步必須是同一筆交易的狀態機，不能讓行政在步驟 2 中途離開就產生半套資料。建議：三個端點各自冪等，且由 appointments 上的 check_in_status + session_records.payment_status + receipts 三者共同決定目前該顯示哪一步。

A4　衝突檢查缺一層：只擋診間，不擋心理師本人

-- 現行唯一的衝突檢查 · routers/appointments.py:614 _check_room_conflict()
SELECT id FROM appointments
WHERE room_id = :room_id AND status != 'cancelled'
  AND time_range && tstzrange(:start, :end)
LIMIT 1;   -- 只看 room_id，完全不看 therapist_id
兩個後果 ① 同一位心理師可以被排進兩間診間的同一時段，系統毫無阻擋。
② 視訊與外展不佔診間（room_id 可為 NULL），所以它們目前完全沒有任何衝突檢查。定稿 Q2 明確定案「兩層都做」，而心理師端的「時間優先」表單流程（A5）更是把這層檢查當作前置條件 —— 沒有它，「系統列出可用診間」這一步無從開始。

A5　表單流程反轉：診間優先 → 時間優先

現況診間優先

cases/page.tsx:1436 AppointmentForm：先選個案 → 選診間 → 選日期時間。診間清單是全部 12 間的靜態下拉。

定稿 F5時間優先（兩端一致）

諮商類型 → 個案 → 日期 → 開始時間 → 時長 → 系統列出可用診間 → 繳費方式。
時長必須在診間之前，因為 90 分鐘與 60 分鐘可用的診間不一樣。

需要一個現在不存在的端點：「給定心理師 + 起訖時間 + 時長，回傳可用診間清單」，且每張診間卡要帶：是否被占用、占用者姓名與時段、⭐ 是否為該個案上次使用、👶 是否遊戲室、是否大間。排序規則（原型 JS 已寫死）：未占用優先 → 上次使用 −100 → 時長≥90 且大間 −50 → 遊戲室 +30。

A8　實習心理師共用帳號

定稿 Q3 採 A 案：單一共用帳號，登入當下填一次姓名，整個工作階段的操作與紀錄都掛這個名字，登出即清除；畫面顯示為「實習心理師（魏啓倫）」。

稽核弱點（診療所已知悉並接受）共用帳號讓異動紀錄無法從系統層面證明是誰做的，只能靠自填姓名。目前僅 1 位實習生，人數變多再改為一人一帳號。
技術上需要：登入時填的姓名 → 寫進 JWT claim → 每一次寫入都落到 audit_log.actor_name（新欄位）、行政流程提醒的勾選紀錄、以及預約的建立者顯示。audit_log.changed_by 只有 user_id，不足以還原。
