## 1 · 這份文件要解決的問題

現在的系統是「一套諮商系統」。它從頭到尾假設一件事：**凡是會用到空間、會收錢、會有心理師參與的，就是一次諮商**。

這個假設在只做諮商的時候完全正確，而且讓系統寫得又快又準。但診所一旦開出第二條業務線——課程、工作坊、團體、企業方案——這個假設就會以三種方式失效：

**第一種：空間會被重複賣。**
空間的總量是固定的。四樓有幾間晤談室、五樓的雲燈教室一次只能辦一場活動，這件事不會因為診所多開了一條業務線而改變。但如果每條業務線各自記著「我訂了哪些時段」，系統就沒有任何一個地方知道「這個時段到底有沒有人」。資源的真相散在各處，等於沒有真相。

**第二種：帳會對不起來。**
診所只有一個櫃檯、一個收銀、一套報表。不論客人是來談話、來上課、還是來租場地，錢都從同一個窗口進來。如果每條業務線各記一本帳，月底就沒有任何一份報表能回答「這個月到底收了多少錢」——而「當日現金加匯款等於當日收入」這條最基本的對帳等式，會變成無法驗證的事。

**第三種：看不見客人的全貌。**
一位個案諮商告一段落，轉去上正念課程；一位課程學員上完課，決定開始個別晤談。如果諮商有一份名單、課程有另一份名單，這兩件事在系統裡就是兩個互不相識的人。診所於是永遠無法回答一個很值錢的問題：**我們的客人是怎麼在不同服務之間流動的？**

這三件事有一個共同的形狀：**有些東西屬於「業務怎麼跑」，會隨營運調整；有些東西屬於「資源與事實」，不能隨業務改變。**現在它們混在一起。

這份文件的目的，是把它們分開，並說明分開之後整間診所的系統長什麼樣。

## 2 · 核心概念：兩種系統，兩種責任

### 2.1 業務流程（Pipeline）

業務流程是一條**流水線**：一件事從頭到尾會經過哪些站、每一站誰做什麼、什麼條件才能往下一站。

諮商的流水線是：

```
詢問進案 → 派案媒合 → 心理師承接 → 初診預約 → 初診報到
  → 轉為正式個案 → 續診循環（預約 → 報到 → 收款 → 開據）
  → [機構案] 核銷請款 → 撥款入帳
  → 結案 ／ 流失 ／ 復案
```

流水線的特徵：

- **它會變。** 診所改了派案規則、加了一道行政確認、調整了核銷時程，流水線就跟著改。這是正常的，系統必須讓它容易改。
- **它只擁有「流程狀態」。** 「這個媒合案在等心理師回覆」「這筆預約還沒報到」「這個核銷案已送出」——這些是流程自己的事。
- **它不擁有資源，也不擁有錢。** 流水線不能自己記著「這間診間被我訂走了」，也不能自己記著「這筆收了八百塊」。它必須去跟管這些事的子系統**申請**與**登記**。

每一條新業務線，就是一條新的流水線。課程有自己的流水線（招生 → 報名 → 繳費 → 開課 → 出席 → 結課），它跟諮商的流水線完全不同——而這沒有關係，因為它們共用同一批子系統。

### 2.2 資源子系統（Resource Subsystem）

子系統管的是**事實**：這個時段這間房有沒有人、這個人是誰、這筆錢收了沒有。

子系統的特徵：

- **它不能變，或者說：它的規則對所有業務一視同仁。** 不論上層跑的是諮商還是課程，「同一間房同一時間只能有一件事」這條規則都一樣。
- **它是該類事實的唯一來源。** 要知道空間有沒有空，只能問空間子系統；要知道今天收了多少錢，只能問財務子系統。沒有第二個地方存著同一件事的另一個版本。
- **它不知道業務細節，也不需要知道。** 空間子系統只需要知道「有人要在 11/12 14:00–15:00 用 2A，佔用的理由是某筆編號 R-20261112-T003-001 的事」。那筆事是諮商、是課程、還是督導，它不在意。

### 2.3 分界線：誰擁有「事實」

這是整套架構唯一需要記住的判準：

| 問題 | 答案的性質 | 歸屬 |
|---|---|---|
| 這個個案在流程的哪一站？ | 流程狀態 | 業務流程 |
| 這個時段 2A 有沒有人？ | 資源事實 | 資源佔用（基礎事實） |
| 這個人是誰、資料齊不齊？ | 身分事實 | 對象管理（基礎事實） |
| 這個月認列了多少收入？ | 財務事實 | 帳本（基礎事實） |
| 今天櫃檯收了多少現金？ | 財務事實 | 帳本（基礎事實） |
| 撥款什麼時候進銀行、進了多少？ | 財務事實 | 帳本（基礎事實） |
| 這筆核銷案送出去了沒？退回要補什麼？ | 過程狀態 | 核銷模組（中介） |
| 這筆核銷案申請了多少？ | 快照 | 核銷模組（中介） |
| 這筆核銷案裡裝了哪些錢？ | 指向帳本的列 | 核銷模組持有指向，金額在帳本 |

最後三列是這套架構最細緻、也最容易做錯的地方。**核銷案管的是「請款這件事的過程」，不是「錢」。**過程會變、會退回重來；錢是事實，認列與入帳兩個端點一旦寫下就不動。

這個分界重要到值得單獨一節說明，見 §5——而且現行程式碼正是在這個分界上出錯的（§5.3）。

### 2.4 為什麼這樣切，而不是切成「模組」

「模組化」通常是按畫面切：個案管理、預約管理、財務管理。那樣切的問題是，每個模組都會為了自己方便，把別人的事實抄一份在自己身上——於是同一件事有了三個版本，而三個版本一定會分岔。

按「誰擁有事實」切，得到的是另一種形狀：**少數幾個深而穩的子系統，加上多條淺而靈活的流水線。**新業務的成本因此落在流水線上（便宜、可改），而不是落在子系統上（昂貴、不該常改）。

## 3 · 分層架構

整套系統分成五層。由下往上：

```
┌──────────────────────────────────────────────────────────────┐
│ L3 · 介面層：角色工作台                                       │
│    櫃檯行政 ／ 心理師 ／ 會計 ／ 管理者                       │
│    （同一批事實，依角色呈現成不同的工作畫面）                  │
├──────────────────────────────────────────────────────────────┤
│ L2 · 業務流程層：流水線           變動頻率：營運調整時          │
│    諮商 ／ 課程 ／ 場地租借 ／ 活動 ／ 未來新業務…              │
│    擁有流程狀態。不擁有資源，不擁有帳。                         │
├──────────────────────────────────────────────────────────────┤
│ L1.5 · 中介模組層：被多條流程共用   變動頻率：外部換約時         │
│    核銷案 ／ 心理師酬勞 ／ 報價與費率                          │
│    規則來自外部（政府、機構、聘約），有自己的版本。              │
│    紀律：只存當時算出的答案（快照），不回頭重算。                │
├──────────────────────────────────────────────────────────────┤
│ L1 · 基礎事實層：事實的唯一來源     變動頻率：以年計／幾乎不變    │
│    ① 對象管理   ② 資源佔用   ③ 帳本                           │
│    紀律：只增不改。寫入口徑窄。等式持續被檢查。                  │
│    ＋ 外部給付方介面（機構／保險／企業，可插拔）                │
├──────────────────────────────────────────────────────────────┤
│ L0 · 基礎服務層：身分、權限、編號、稽核、通知                   │
│    （誰在操作、誰能看什麼、每件事的唯一編號、改了什麼留痕）      │
└──────────────────────────────────────────────────────────────┘
```

**為什麼是五層而不是三層。**層與層的分界不只是「誰擁有事實」，還有一個同樣重要的維度：**這一層的規則多久會變一次。**

把三者放在一起看，分層的理由就很清楚了：

| 層 | 規則來自 | 多久變一次 | 出錯的代價 |
|---|---|---|---|
| L2 流程 | 診所自己的營運決定 | 隨時 | 操作不順，改回來就好 |
| L1.5 中介 | 政府、機構、聘約 | 每次換約、每年 | 某個方案算錯錢，影響該方案的案件 |
| L1 基礎事實 | 會計與資源的本質 | 幾乎不變 | **全盤帳目失真，而且不會立刻被發現** |

一個每年會變的東西（例如核銷辦法）如果寫在 L1 裡，就會逼著 L1 每年被改一次——而 L1 是「不能錯」的那層，每次改都是一次風險。反過來，如果把核銷寫在 L2 的諮商流程裡（現在就是這樣），那未來課程要核銷時只能複製一份，而兩份一定會分岔。

**L1.5 的存在，就是為了讓 L1 可以真的不動。**

**依賴方向只有一個：上層依賴下層，下層永不依賴上層。**

這句話的實際意義是：空間子系統的程式碼裡，不會出現「諮商」或「課程」這兩個字。它只認得「有一筆佔用，主人是某個編號」。因此新增一條業務線，不需要動空間子系統一行。

這不是理論。這個架構在本專案已經實作過一次並驗收通過：機構合約子系統（文件 07）就是用這個方式接進主系統的——主系統定義了一組介面（八支方法），機構子系統去實作它，而**主系統的程式碼從不引用機構子系統**。驗收標準當時訂得很具體：「把機構子系統整包搬走，主系統其餘程式碼要還能運作，只是退化成純自費診所。」這條標準現在仍然成立，而它正是本文要推廣到空間與財務的那個模式。

## 4 · 三個核心子系統

### 4.1 ① 對象管理子系統

**它管什麼：** 所有跟診所有金錢或服務關係的人與單位，是同一本名冊。

目前系統裡只有「個案」這一種對象。但實際上診所面對的對象至少有六種：

| 對象類型 | 例子 | 現在怎麼存 |
|---|---|---|
| 個案 | 來談話的人 | 完整的個案資料表 |
| 伴侶／家庭 | 合併計費的一組人 | 一筆特殊個案 ＋ 成員關聯 |
| 學員 | 來上課的人 | **不存在** |
| 借用人 | 租場地的人或單位 | **一個純文字欄位** |
| 外聘講師 | 來授課的外部老師 | **一個純文字欄位** |
| 機構 | 衛生局、國軍、學校 | 機構資料表 |

「純文字欄位」的意思是：系統知道那裡寫著「王小明」四個字，但不知道這個王小明是不是上個月來談話的那個王小明。這就是為什麼目前無法回答「客人如何在服務之間流動」。

#### 核心設計：資料完整度分級

這是你提到的那個關鍵點——「預約系統裡的個案必須有完整資料，但初診時還沒有」——的正式解法。

重點不是「資料不全就不能用」，而是：**資料的完整度決定這個對象能做哪些事。**

| 等級 | 名稱 | 必備資料 | 能做 | 不能做 |
|---|---|---|---|---|
| **L0** | 詢問者 | 姓名、聯絡方式 | 進入媒合、被派案、接受諮詢 | 不能預約任何佔用資源的事 |
| **L1** | 待初診／學員 | ＋ 出生年月日、聯絡電話 | 預約一次初診；報名課程；產生自費帳 | 不能續診；不能動用機構補助 |
| **L2** | 正式對象 | ＋ 身分證號、地址、緊急聯絡人 | 續診循環；動用機構補助與核銷；開立機構收據 | — |
| **L3** | 機構關聯對象 | ＋ 該機構配發的個案代號 | 該機構方案的核銷請款 | — |

這個分級帶來三個好處：

1. **升級的時機由流程決定，而不是由系統硬擋。** 「初診報到時補齊資料」就是一次 L1 → L2 的升級，而這個升級動作有一個明確的位置（櫃檯報到的那一格），不會變成「某個欄位沒填，然後在三週後的核銷階段才爆掉」。
2. **每條業務線自己宣告它需要什麼等級。** 課程報名可能只需要 L1；機構諮商需要 L2 甚至 L3。這是流水線的設定，不是子系統的規則。
3. **缺什麼資料由子系統算出來告訴流程**，而不是讓每個畫面各自寫一份「要填哪些欄位」的清單。這點本專案在 2026-09-11 已經踩過一次：初診表單問的欄位跟轉正式所需的欄位不一致，櫃檯填完以為好了，按下轉正式才跳出「還需要出生日期」。

#### 身分與參與要分開

一個人（對象）可以同時有多個**參與**：

```
王小明（一位對象，L2）
  ├─ 參與①：個別諮商（心理師 T003，衛生局方案，進行中）
  ├─ 參與②：正念課程第 3 期（學員，已繳費，上課中）
  └─ 參與③：家庭會談（作為另一個家庭案的成員）
```

- **對象**是子系統的事實：一個人就一筆，不論他參加幾種服務。
- **參與**是業務流程的狀態：每條流水線管自己的參與。

這樣分開之後，「諮商轉課程」在系統裡是一件自然的事——同一個對象多了一筆參與。報表要算轉換率，只要去數「同時有參與①與參與②的對象」。

#### 子系統對外的承諾（介面）

對象子系統對所有業務流程提供這些能力，而且只有這些：

- 查某對象目前的資料等級
- 查某對象距離某個等級還缺哪些欄位
- 建立／升級一個對象（含必要的稽核留痕）
- 查某對象的所有參與（跨業務）
- 依姓名／電話／編號找人（含「是不是同一個人」的疑似重複提示）

### 4.2 ② 空間與時間子系統

**它管什麼：** 一句話——**資源在某個時間有沒有被佔用**。

#### 資源不只是房間

這是現行設計最大的盲點。診所的「資源」實際上有三類，而它們都會衝突：

| 資源類型 | 例子 | 衝突規則 |
|---|---|---|
| **場地** | 四樓晤談室、五樓雲燈教室 | 同一場地同一時間只能一件事 |
| **人** | 心理師、外聘講師 | 同一人同一時間只能在一個地方 |
| **設備** | 兒童遊戲室教具、視訊設備 | （視未來需要） |

**人也是固定資源**，這點必須講清楚。一位心理師在 14:00 不能同時出現在 2A 和 3B；他在外展的時候也不能同時在所內接個案——即使外展不佔用診所的任何房間。目前系統擋了房間，但完全沒有擋人（詳見 §7.1）。

因此子系統管的不是「房間預約表」，而是**資源佔用表**：

```
一筆佔用 = 哪個資源 ＋ 哪段時間 ＋ 誰佔的（主人編號） ＋ 佔用類型
```

一次現場諮商會同時產生兩筆佔用：一間房 ＋ 一位心理師。一次視訊諮商只產生一筆：一位心理師。一次外展也只產生一筆：一位心理師。一場雲燈教室活動產生：一個場地 ＋ 一位講師（若是所內心理師）。

這個模型讓「視訊與外展不佔房間但佔人」這件事第一次被正確表達——目前它是靠「房間欄位可以留空」勉強繞過的。

#### 四條不可違反的規則

1. **總量固定。** 資源清單是主檔，不是業務可以生出來的東西。新開一條業務線，不會多出一間房。
2. **同一資源同一時間只能一筆有效佔用。** 不論佔用者是什麼業務。
3. **佔用必須有主人。** 每筆佔用都指向一個業務物件的編號；孤兒佔用是資料錯誤。
4. **取消必須釋放。** 業務流程取消了，佔用必須同步消失。這條是系統最容易破的——本專案已經修過一次「取消預約沒還機構額度」的同類問題。

#### 佔用與預約的區別

這是一個容易混淆但必須分清的差別：

- **佔用（Hold）**：資源事實。「2A 在這個時段有人」。由空間子系統擁有。
- **預約（Booking）**：業務事實。「王小明跟林心理師約了這個時段談話」。由業務流程擁有。

一個預約會**造成**一或多筆佔用，但預約本身不是佔用。這個分離讓同一套空間子系統能同時服務諮商預約、課程排程、場地出租、內部會議——它們是四種預約，共用一種佔用。

#### 兩層防護的做法要保留

現行系統在房間衝突上用了一套值得延續的做法：**資料庫層用約束硬擋（絕對不會錯），應用層給人看得懂的錯誤訊息（告訴行政是誰佔的），再加一支跨表檢查當守門員（定期確認沒有破）。**這個三層做法應該原樣套用到新的資源佔用表上——而且因為那時只有**一張**佔用表，資料庫約束就能一次擋掉所有跨業務衝突，不再需要靠應用層補跨表那一段。

#### 子系統對外的承諾

- 查某資源某段時間是否可用
- 查某段時間所有可用資源（排班、找空房）
- 申請佔用（成功則回傳佔用編號；失敗則回傳「被誰佔住」）
- 釋放佔用
- 移動佔用（改時間／改房間，含衝突檢查）
- 產生日曆視圖（給任何業務用的時段矩陣）

### 4.3 ③ 財務與金流子系統

**它管什麼：** 診所所有的錢。一本帳。

#### 核心主張：單一帳本

不論錢的來源是諮商、課程、場地出租、商品販售，它都是**同一本帳上的一列**。

```
一筆帳目 = 日期 ＋ 金額 ＋ 名目 ＋ 付款方 ＋ 來源業務物件 ＋ 收款狀態
```

「來源業務物件」是帳目跟業務的唯一連結。帳本知道「這八百塊是從編號 R-2026…-001 那件事來的」，但不需要知道那件事是什麼。這跟空間子系統的設計是同一個模式。

#### 必須成立的恆等式

這些是財務子系統存在的理由。每一條都應該能被自動驗證，任何一條破了就是資料損壞：

| # | 等式 | 意義 |
|---|---|---|
| F1 | 當日現金 ＋ 當日匯款 ＝ 當日實收總額 | 櫃檯對帳的根本。你特別強調的那一條。 |
| F2 | 每筆帳目：應收 ＝ 已收 ＋ 未收 ＋ 減免 | 單列層級的平衡 |
| F3 | 個案自付 ＋ 外部給付方應付 ＝ 帳目總額 | 拆帳不能漏錢（現行已有此檢查） |
| F4 | 收據金額 ＝ 其對應帳目的實收金額 | **開出去的憑證必須跟帳目吻合**——你提到的那條 |
| F5 | 月報表各業務收入加總 ＝ 該月帳本實收總額 | 報表不能自己算一套 |
| F6 | 心理師酬勞 ＝ Σ(其場次應計基數) − 扣項 | 已有此檢查，要延伸到課程鐘點 |
| F7 | 沒收到錢，不得開立收據 | 已有此檢查 |
| F8 | 收據編號在全系統唯一 | 目前**分屬不同號碼空間**，詳見 §7.2 |

F1 和 F5 是現在**算不出來**的（§7.2 有證據）。這不是程式有 bug，是因為沒有一本共同的帳。

#### 名目（Fee Item）是帳本的維度，不是業務的屬性

這是讓多業務共存的關鍵。「個別諮商費」「團體課程費」「場地租金」「教材費」都是**名目主檔裡的項目**，由管理層維護。新增一條業務線，通常只是新增幾個名目——不需要改財務系統。

而收據上印的名目，必須是帳本上那一列的名目。這就是 F4 的實際意義：收據不是另外寫一張紙，它是帳目的一份憑證。

#### 外部給付方是一個可插拔的介面

機構補助、未來可能的保險給付、企業方案，共同點是「有人代替客人付一部分錢，而且有自己的核銷規則」。

這件事本專案**已經做對了**：主系統定義了一組介面，機構合約子系統去實作。主系統只存「當時算出來的答案」（報價快照）——費率之後改了，已經發生的場次金額不會被改動，因為歷史金額是事實，不是重算出來的結果。

這個設計要原樣保留，並且在概念上明確為：**財務子系統的一個擴充點**。新增一種給付方（例如企業員工協助方案），是寫一個新的實作，而不是改財務子系統。

#### 子系統對外的承諾

- 建立應收帳目（帶名目、金額、付款方）
- 登記收款（現金／匯款／其他，含金額與憑證資訊）
- 開立收據（必須對應已收款的帳目）
- 作廢與重印（留軌跡，不刪資料）
- 查某業務物件的所有帳目
- 查某日／某月的收支總表（對帳與報表的唯一來源）
- 記錄一筆反向更正（更正不改原列）

**不在這裡的：核銷流程。**向機構請款的整個過程——送出、退回補件、再送、追撥款——不屬於帳本。帳本只認兩件事：這筆錢什麼時候被認列、什麼時候真的進來。中間那段過程歸中介模組層，見 §5。

## 5 · 中介模組層：核銷案與同類模組

### 5.1 為什麼兩層不夠

核銷案兩邊都放不進去：

**放不進業務流程層。** 它不是諮商獨有的——只要未來的課程接到同一個政府單位的案子，就應該走同一套請款流程。而且它有自己必須永遠成立的規則（一筆帳目只能被一個核銷案收納、退回補件必須清掉確認閘門），這些規則不該隨哪條流程在用它而改變。

**放不進基礎事實層。** 它的規則**來自外部**——政府的核銷辦法、機構的合約條件。每次換約、每個年度都可能改。把一個每年會變的東西放進「完全不能錯」的那一層，等於讓那層不穩。

所以需要中間這一層：**往下對接帳本，往上被多條流程共用，有自己的版本與改版節奏。**

### 5.2 分層的真正依據：三條時間軸

| 時間軸 | 回答的問題 | 誰擁有 | 會不會變 |
|---|---|---|---|
| **認列** | 服務什麼時候發生 | 帳本（基礎事實） | **永不改**——執行月 |
| **請款** | 什麼時候送出、被退回、補了什麼、再送 | 核銷模組（中介） | 經常改，而且會來回 |
| **入帳** | 錢什麼時候真的進銀行、進了多少 | 帳本（基礎事實） | **永不改**——銀行事實 |

你說「帳本的界線在於有沒有收到款，以銀行為基礎」——這句話我想補完整：**帳本管的是兩個端點（認列與入帳），核銷管的是中間那段過程。**端點是事實，寫下就不動；中間那段會變、會退回重來，所以它需要自己的一層。

這不是新主張。文件 07 在 2026-09-07 就已經裁示：「收入認列＝執行月，永遠不變；核銷是另一條時間軸，中間狀態是機構應收款；撥款入帳不搬月。」當時那是一條規則，現在把它升格成架構的分層依據。

### 5.3 結構上的證據：現在的核銷案同時做了三層的事

核銷案這張表的欄位，實際上分屬三個不同的層：

| 欄位 | 性質 | 該在哪一層 |
|---|---|---|
| `status`（收集中／已送出／已結案）、`docs_waived_at`、`voided_at` | 流程狀態 | 中介層 ✅ 正確 |
| `claim_no`、`applied_amount`、`period_start/end`、`grouping_mode` | 請款快照 | 中介層 ✅ 正確 |
| `received_date`、`received_amount`、`income_tax_amount`、`transfer_fee`、`net_received` | **銀行入帳事實** | **帳本** ❌ 錯層 |

第三類的後果很具體。計算淨入帳的算式寫在核銷模組裡：

```
net_received = received_amount − income_tax_amount − transfer_fee
```

意思是：**所得稅代扣與匯費這兩筆錢，從來沒有進入任何帳本。**它們在核銷案內部被扣掉，所以：

- 損益表看不到這兩項成本——它們不存在於任何一本帳
- 「報表上的收入」與「銀行實際入帳的金額」之間的差額，沒有任何地方解釋
- 若機構核減（申請一萬、只給九千），那一千元現在也只是「兩個欄位的差」，沒有一筆明確的核減紀錄

同時，目前 25 條對帳等式裡，**沒有一條在驗核銷的金額**。只有兩條跟核銷有關：「一筆場次只能被一個核銷案收納」與「核銷案狀態要跟成員紀錄一致」。以下三件事完全沒有被檢查：

- 核銷案的申請金額 ＝ Σ 其收納列的金額
- 淨入帳 ＝ 申請 − 稅 − 手續費
- 入帳的那筆錢，對應到帳本上的哪幾列

而原因正是你診斷出來的：**底下沒有一本帳可以對。**

### 5.4 分層之後長什麼樣

**帳本（基礎事實層）多認三種列：**

| 列的類型 | 什麼時候產生 | 例子 |
|---|---|---|
| 應收認列 | 服務發生時（執行月） | 衛生局方案某場次：機構應付 $1,600 |
| 收款 | 錢實際到帳時 | 撥款入帳 $9,000（現金／匯款／撥款） |
| 費用 | 伴隨收款發生 | 所得稅代扣 $450、匯費 $30 ← **現在被吃掉的那兩筆** |
| 核減 | 給付方少給時 | 核減 $1,000（需註明原因） |

**核銷模組（中介層）只記四件事：**

1. 這個核銷案收納了哪些應收認列列（只存指向，不存金額副本）
2. 請款流程的狀態與時間（送出、退回、補件、再送、結案）
3. 該機構要求的文件清單與完成狀態
4. 申請金額快照（送出那一刻算出的答案，之後不重算）

**入帳時，核銷模組請帳本記三到四列**（收款、稅、手續費、必要時核減），自己不存任何金額事實。

**由此得到一條新的恆等式：**

```
Σ(該核銷案的收款列) ＋ Σ(其費用列) ＋ Σ(其核減列) ＝ 申請金額
```

任何差額都必須有一列解釋它。錢不能默默消失，這是把核銷案從「兩個欄位相減」變成「帳上說得清楚」的關鍵。

### 5.5 共用的判準：收納的是帳目，不是場次

你問：未來課程若也需要核銷，只要是同一個政府單位的案子，能不能走同一套流程？

**能，而且條件只有一個——核銷案收納的必須是「帳本上的應收列」，而不是「諮商場次」。**

現在是後者：核銷收納列指向場次紀錄，而場次紀錄綁定一筆預約、且必填心理師。所以一門多人課程的學費，**結構上裝不進核銷案**——不是因為功能沒做，是因為形狀不對。

改成收納帳目之後，任何業務只要產生應收列就能被核銷，核銷模組一行都不用改。

這是一條可以驗證的架構判準，不是原則宣示：**拿一筆課程學費，試著把它收納進一個核銷案。如果需要改核銷模組，分層就沒做對。**

### 5.6 同一個形狀的還有兩個模組

核銷不是特例。中介層一共有三個成員，性質完全一樣：

| 模組 | 與帳本的關係 | 規則來自 | 變動頻率 |
|---|---|---|---|
| **核銷案** | 消化應收列 → 產生收款列 | 政府與機構的核銷辦法 | 每次換約 |
| **心理師酬勞** | 消化應計列 → 產生支出列 | 聘約（抽成、回饋制、外出保底、課程鐘點） | 每次調整聘約 |
| **報價與費率** | 決定應收列的金額 | 機構合約清冊（54 方案、7 種定價） | 每年換約 |

三者共同的紀律只有一條：**只存當時算出的答案（快照），不回頭重算。**

這條紀律在報價上已經實施（存報價快照，費率改了歷史金額不動），在酬勞上已經實施（已發放的酬勞是歷史事實，重算不覆蓋）。**核銷是三者中唯一還沒補上的**——而它恰好是金額最大、最常被外部規則改動的那一個。

### 5.7 什麼才算「有自己規則的資料庫」

你說：就算某個資料只會被一條流程用到，也不該把邏輯寫死在那條流程裡，而該獨立成有自己規則的資料。

這個方向對，但需要一個判準，否則每張表都會被叫做「子系統」，而分層就失去意義。判準是：

> **能不能寫下一條關於這份資料、而且不論哪條流程在用它都必須成立的等式？**

| 資料 | 等式 | 判定 |
|---|---|---|
| 帳本 | 現金 ＋ 匯款 ＝ 實收總額 | ✅ 獨立，而且是最底層 |
| 資源佔用 | 同一資源同一時間最多一筆有效佔用 | ✅ 獨立（基礎事實） |
| 對象 | 有病歷號 ⇔ 已轉正式 | ✅ 獨立（基礎事實） |
| 核銷案 | 申請金額 ＝ Σ收納列；一列只能被收納一次 | ✅ 獨立（中介層） |
| 酬勞 | 酬勞總額 ＝ Σ應計 − 扣項 | ✅ 獨立（中介層） |
| 媒合案 | 狀態＝已預約 ⇒ 存在一筆未報到的預約 | ⚠️ 見下 |
| 某個預約的備註欄 | 寫不出來 | ❌ 純流程狀態 |

媒合案那一列值得說明，因為它是個邊界案例：它確實有等式，但那條等式**跨越了媒合與預約兩邊**。這種情況下媒合仍然是流程，而那條等式的身分是「**流程必須被強制檢查的完整性條件**」——它要被寫成對帳等式持續檢查（本專案已經做了，2026-09-11 補了兩條），但不需要把媒合升格成子系統。

分界是：**等式只關於這份資料自己 → 獨立的子系統或模組。等式關於兩份資料之間的關係 → 它是流程的完整性條件，由檢查器守。**

### 5.8 「不能出錯」需要機制，不是決心

你說最底層必須完全不能動、不能出錯。這件事要成立，需要四個具體機制，缺一不可：

| # | 機制 | 說明 | 現狀 |
|---|---|---|---|
| 1 | **只增不改** | 帳本的列寫下就不動。要更正，記一筆反向列，不改原列。這樣任何時點的帳都能重現，稽核也查得到 | ❌ 現在帳是可以直接改的 |
| 2 | **寫入口徑窄** | 上層不能直接寫帳本，只能透過少數幾支定義好的動作：認列、收款、開據、作廢、反向更正 | ❌ 現在四張表各自被多處直接寫 |
| 3 | **等式持續被檢查** | §4.3 的八條恆等式，每次資料變動與每日都跑，不是上線前跑一次 | ⚠️ 架構已在（25 條對帳等式＋76 條覆蓋檢查），但帳本相關的那幾條還算不出來 |
| 4 | **快照原則** | 歷史金額是事實。規則改了，已經發生的不重算 | ✅ 報價與酬勞已實施；核銷待補 |

第四條已經做到，而且是在真實複雜度下（54 個機構方案）做到的——這說明這套紀律在本專案實施得起來。前三條是這次重構要補的。

## 6 · 業務流程如何接子系統

### 6.1 原則：每一步宣告它需要什麼

業務流程的每一站，都用同一種方式跟子系統互動：

```
第 N 站：
  前置條件 — 需要哪個等級的對象資料？需要哪些資源可用？
  向子系統申請 — 要佔用什麼？要建立什麼帳目？
  自己記什麼 — 只記流程狀態
  失敗怎麼辦 — 哪些申請失敗要整站退回
```

這段「宣告」是流程的設定，寫在流程裡，可以隨營運調整。子系統只負責回答「可以」或「不行，因為…」。

## 7 · 現狀盤點：我們離這個架構有多遠

以下是 2026-11-04 對現行程式碼的實地查證結果。每一項都是實際量過的，不是推測。

### 7.1 空間：三套各自獨立的佔用模型，而「人」完全沒有被擋

現在有**三種**東西會佔用空間，而它們是三種不同的資料結構：

| 佔用者 | 資料結構 | 衝突保護 |
|---|---|---|
| 諮商預約 | 房間 ＋ 時段 | 資料庫約束（同表內） |
| 場地租借 | 房間 ＋ 時段 | 資料庫約束（同表內） |
| 雲燈教室活動 | **沒有房間欄位**，只有活動時段（＋場佈時段） | 獨立的資料庫約束 |

前兩者的跨表衝突，靠一支應用層模組擋，並有一支跨表檢查當守門員——這套做法本身是對的，而且註解寫得很清楚：資料庫的排除約束只能作用在一張表上，所以跨表那一層必須在應用層補。

但問題有兩個：

**第一，雲燈教室完全不在這套檢查裡。**它有自己的時段欄位、自己的約束，而且不經過那支共用的衝突模組。等於五樓是一個獨立宇宙。

**第二——也是更嚴重的——心理師的時間完全沒有被檢查。**整個後端找不到任何一處在建立預約時檢查「這位心理師這個時段是不是已經有別的事」。這件事在 2026-08 的可行性研究（文件 01 §A4「衝突檢查缺一層：只擋診間，不擋心理師本人」）就被列為八項架構級衝突之一，至今仍然成立。

實際後果：一位心理師可以被排在 14:00 的 2A 現場晤談，同時被排在 14:00 的視訊，同時被排在 14:00 的外展——系統三次都會接受。

這一項是本文 §4.2「人也是固定資源」那個主張最直接的證據。

### 7.2 財務：四本平行的帳，兩套收據號，對帳等式算不出來

錢現在記在**四個互不相干**的地方：

| 帳 | 存在哪 | 收據怎麼開 |
|---|---|---|
| 諮商收入 | 場次紀錄（綁定一筆預約，一對一） | 收據表（綁定場次） |
| 場地費 | 場地租借自己的金額欄位 ＋ 付款方 | **不經過收據表** |
| 活動／講師費 | 活動自己的講師費欄位 ＋「是否入診所帳」 | **不經過收據表** |
| 商品販售 | 商品販售表 ＋ **自己的收據號欄位** | **自己一套號碼（P 開頭）** |
| 零用金 | 零用金表，用「結餘」欄位滾動 | 不適用 |

兩個直接後果：

**第一，§4.3 的 F1 與 F5 現在算不出來。**要回答「今天收了多少錢」，必須分別去四張表撈，各自判斷哪些算收入、哪些作廢、哪些其實沒進診所帳——而且沒有任何一個地方保證四者加起來就是全部。「現金加匯款等於總收入」這條等式**沒有一個單一的左式可以算**。

**第二，收據號分屬兩個號碼空間。**諮商收據和商品收據由兩套序號各自產生。系統現在有一條跨表檢查在擋它們撞號——這條檢查之所以存在，正是因為結構上允許撞號。而更根本的問題是：場地費和活動費**根本沒有收據**，所以「開出去的憑證跟帳目吻合」這件事，在那兩類收入上無從談起。

另外，「現金／匯款」這組付款方式的選項，散落在程式碼 21 處各自寫死。新增一種收款方式（例如行動支付、刷卡），要改 21 個地方。

### 7.3 對象：非諮商的對手方沒有身分

- 場地借用人：一個純文字欄位。
- 活動借用單位：一個純文字欄位。
- 外聘講師：一個純文字欄位。
- 學員：不存在。

所以「這位來租場地的督導，是不是我們的心理師」「這位學員是不是去年那位個案」——系統都無法回答。§1 的第三種失效現在就已經發生了，只是還沒有課程業務讓它變得明顯。

值得一提的是，伴侶案的設計是個好樣本：它用「一筆特殊對象 ＋ 成員關聯」表達「合併計費但各自是獨立個人」，並且解決了「機構核銷以人為單位、伴侶案沒有真人身分」這個難題——做法是讓合療預約選擇付款方。這個「對象 ／ 參與 ／ 付款方」三者分離的思路，正是 §4.1 要推廣的。

### 7.4 編號：七個獨立的序號空間

目前有七套編號各自配號：個案、伴侶案、預約、收據、商品、場地租借、媒合。它們已經共用一張序號表（這是對的，解決了「刪一筆就重號」的老問題），但**規則各自寫死**。新增一條業務線就要再加一套，而且每一套都有自己的日期與前綴規則。

這裡的改進方向不是「統一成一種編號」（各業務本來就需要可辨識的前綴），而是把「配號」變成基礎層的一項服務：業務宣告它要的格式，基礎層保證唯一與不重號。

### 7.5 已經做對的事：依賴反轉已經驗收過一次

機構合約子系統是本專案最值得複製的既有成果：

- 主系統定義介面（八支方法：三支查詢、五支命令），機構子系統實作它。
- **主系統的程式碼從不引用機構子系統。**驗收標準是「把子系統整包搬走，主系統還能運作，只是退化成純自費診所」。
- 主系統只存報價快照——當時算出的答案。費率後來改了，歷史金額不變。
- 54 個機構方案的全部變異（7 種定價、8 種額度規則、5 種核銷時程、兩種金流方向）都關在子系統裡，主系統只增加 6 個欄位，而且**形狀不隨方案數增加而改變**。

這證明這個架構模式在本專案可行、而且已經承受過真實複雜度的考驗。空間與財務要做的，是同一件事再做兩次。

### 7.6 現狀總結

| 子系統 | 現狀 | 距離目標 |
|---|---|---|
| 外部給付方介面 | **已完成**，依賴反轉驗收通過 | 可直接沿用；概念上是帳本的擴充點，實作上屬中介層 |
| 對象管理 | 只有個案，其餘對手方是純文字；資料等級是隱性的 | 需要抽出對象／參與兩層，並把等級明確化 |
| 空間與時間 | 三套模型並存；人的衝突完全沒擋 | 需要統一成單一資源佔用模型（含人） |
| 財務與金流 | 四本平行帳；兩套收據號；對帳等式算不出來 | 需要統一成單一帳本 |
| 核銷（中介層） | 同時存著流程狀態、請款快照與**銀行入帳事實**；稅與匯費沒進任何帳；收納的是場次而非帳目，所以課程裝不進去；金額無任何對帳等式 | 需要把入帳事實下推到帳本，收納對象改成帳目（§5.3–§5.5） |
| 編號、稽核、權限 | 已有序號表、稽核留痕、角色權限 | 整理成基礎層服務即可 |

**一句話：三個核心子系統裡，已經做好一個（給付方介面），另外兩個（空間、財務）的邏輯都寫在諮商流程裡面，需要抽出來。**

## 8 · 會遇到的問題與難點

這些是這個架構真正的風險，不是形式上的風險清單。

### 8.1 「人」作為資源，排班與意願的界線在哪

把心理師當成固定資源之後，衝突檢查變嚴格了，這會立刻碰到一個管理問題：**系統要不要知道心理師的可排班時段？**

- 如果不知道：只能擋「同時兩件事」，不能擋「排在他不上班的時間」。
- 如果要知道：就需要一份班表主檔，而班表的維護成本、以及「臨時調整」的彈性，是管理層要決定的事。

這件事會影響課程更深——課程通常提前好幾週排定整期的時段，一旦講師的時間沒被系統知道，衝突會在開課前才被發現。

### 8.2 統一帳本的遷移風險

現有的錢散在四張表裡，而且**歷史金額是事實**。遷移時不能重算，只能原樣搬——意思是新帳本必須能容納舊資料的所有形狀，包括那些當初設計得不太一致的部分（例如零用金用的是滾動結餘，而不是收支列）。

這裡的原則應該沿用機構子系統那條：**存的是當時的答案。**遷移是搬運，不是重新計算。而遷移之後，必須能用新帳本重現舊報表的每一個數字——這是遷移唯一可接受的驗收標準。

### 8.3 核銷流程與帳本的界線容易再混淆

§2.3 說過：核銷案是流程，裡面裝的錢是帳本列。這個界線在實作上很容易被打破，因為核銷流程自然會想在自己身上記「這個核銷案總共多少錢」。

一旦記了，就有兩個版本的同一個數字，而它們一定會分岔。正確做法是核銷案只記「裝了哪些帳目」，金額永遠從帳本算。這是本專案已經踩過的那類錯誤——「同一份知識抄成多份，一定會分岔」是現行開發規則裡明文記下的三種反覆錯誤之一。

### 8.4 彈性的界線：什麼情況該改子系統

這是最需要事先講清楚的判準，否則「子系統要穩定」會變成一句空話。

| 情況 | 處理方式 |
|---|---|
| 新增一條業務線 | 寫一條新流水線。子系統不動。 |
| 新增一種收費名目 | 名目主檔加一筆。程式不動。 |
| 新增一種付款方式 | 財務子系統的付款方式主檔加一筆。 |
| 新增一種外部給付方（保險、企業） | 寫一個新的給付方實作。財務子系統不動。 |
| 新增一間房、一個場地 | 資源主檔加一筆。程式不動。 |
| 出現一種**新的資源類型**（例如需要管理設備） | **要動空間子系統**——這是罕見且昂貴的。 |
| 出現一種**新的錢的形狀**（例如需要分期、需要預收款餘額） | **要動財務子系統**——同上。 |

最後兩列是真正的「改子系統」場景。它們應該很少發生，而且每次發生都值得當成一次架構決策來處理，不是順手加個欄位。

### 8.5 權限會變複雜

現在的權限是四種角色對應固定的頁面範圍。多業務之後會出現新問題：

- 課程的行政人員，該不該看得到諮商個案的資料？
- 心理師看得到自己的諮商個案，那他看不看得到自己帶的課程學員？
- 會計需要看全部的帳，但需不需要看得到個案的診療內容？

原則上，權限應該從「能看哪些頁面」轉為「能看哪些對象、哪些帳目、哪些資源」——因為頁面會隨業務增加，而對象／帳目／資源是穩定的三類事實。

### 8.6 這不是一次換皮，是重寫核心

必須對管理層講清楚的成本面：空間與財務的邏輯目前分散在諮商流程裡（最大的那支預約程式超過 1,500 行，帳冊超過 1,000 行）。把它們抽出來，不是加功能，是把既有功能搬到新的位置並重新驗證。

好消息是驗證方法已經到位：目前有 251 條自動測試、25 條跨表對帳等式、76 條業務覆蓋檢查。這三層驗證是這次重構敢動核心的前提——抽出子系統之後，這些檢查必須全綠，而那正是「搬完之後功能沒少」的客觀證據。

## 9 · 需要管理層決定的事

這些問題系統無法自己決定，而且答案會改變架構。

**關於空間與人**

1. 心理師的可排班時段要不要進系統？若要，由誰維護、多久調整一次？
2. 外展（在機構場地進行）要不要佔用心理師的時間？（技術上應該要，但這會擋掉一些目前排得出來的班）
3. 五樓雲燈教室要不要納入同一套資源清單？（目前它是獨立的）

**關於對象**

4. 課程學員需要到哪個資料等級？（建議 L1：姓名、生日、電話）
5. 同一個人在諮商與課程之間，要不要共用一個對象紀錄？（建議要——這是「看見客人全貌」的前提，但牽涉個資範圍）
6. 場地借用人、外聘講師要不要建立正式紀錄？

**關於財務**

7. 課程收入的名目怎麼定？（決定報表的分類軸）
8. 課程費用退費規則？（缺課退不退、第幾堂之後不退）
9. 心理師帶課程的報酬模式：鐘點、抽成、還是另一種？（會新增一種酬勞算式）
10. 課程收據的名目與編號，要不要跟諮商收據共用一套號碼？

**關於範圍與順序**

11. 第一條新業務線確定是課程嗎？還是有其他更先的？
12. 新舊並行的期間可以接受多長？（遷移期間兩套帳並存是最危險的狀態）

## 10 · 切入點與順序

重構的順序不是按模組大小，而是按**依賴關係**：被依賴最多的最先做。

### 第一階段：把「人」納入資源（最小、最急、立刻有價值）

把心理師的時間納入衝突檢查。這件事：

- 不需要新業務線就有價值（現在就能防止排班撞班）
- 是文件 01 列為架構級衝突、至今未解的八項之一
- 規模最小，但會迫使我們先決定「資源佔用」這個模型長什麼樣

這一步做完，空間子系統的雛形就出來了。

### 第二階段：統一資源佔用模型

把諮商預約、場地租借、雲燈教室三套各自的佔用，合併成一張資源佔用表。做完之後：

- 資料庫約束可以一次擋掉所有跨業務衝突，不再需要應用層補跨表那段
- 新增任何業務線，排程部分零成本
- 日曆視圖變成子系統提供的能力，任何業務都能用

### 第三階段：統一帳本

把四本平行帳合併成一本。這是最大的一步，也是最需要小心遷移的一步。驗收標準明確：**遷移後能用新帳本重現舊報表的每一個數字，而且 §4.3 的八條等式全綠。**

做完之後，「當日現金加匯款等於當日收入」第一次成為可以自動驗證的事。

### 第四階段：把核銷案下推成中介模組

帳本存在之後，核銷案才有東西可以對接。這一步做三件事：

1. **入帳事實下推到帳本**——`received_amount`、`income_tax_amount`、`transfer_fee` 不再存在核銷案上，改成請帳本記收款列與費用列。所得稅與匯費第一次成為帳上看得到的成本。
2. **收納對象從場次改成帳目**——這一步讓核銷案脫離諮商，任何業務的應收列都能被收納。
3. **補上三條對帳等式**——申請金額＝Σ收納列、收款＋費用＋核減＝申請、入帳對應到帳本哪幾列。

驗收標準（§5.5）：拿一筆課程學費，試著收納進一個核銷案。**如果需要改核銷模組，這一步就沒做對。**

### 第五階段：抽出對象／參與兩層

把對象從個案裡抽出來，把「參與」留給各業務流程。這一步做完，才能接新業務線的對象（學員、借用人、講師），也才能回答跨業務的客人流動問題。

### 第六階段：第一條新業務線

此時課程流程只需要寫它自己的流水線——招生、報名、出席、結課——其餘全部向下層申請：空間向資源佔用申請、錢向帳本登記、若有補助向核銷模組收納、人向對象名冊登記。這一步的規模，應該顯著小於前五階段的任何一階段。**如果不是，就說明前五階段沒做乾淨。**這是整個架構最好的驗收標準。

### 為什麼這個順序

每一階段都獨立有價值，不必等到最後才看得到東西；而且每一階段都讓下一階段變簡單。最重要的是：**前五階段完全不需要新業務線存在就能做**，所以課程的規劃可以跟重構並行，不互相等待。

## 11 · 詞彙表

給後續討論與製圖用的一致用語。

| 詞 | 意義 | 歸屬 |
|---|---|---|
| **業務流程（Pipeline）** | 一條從頭到尾的流水線，例如諮商、課程 | L2 |
| **流程狀態** | 流水線自己的進度，例如「等心理師回覆」 | L2 |
| **子系統（Subsystem）** | 某類事實的唯一來源，規則跨業務一致 | L1 |
| **對象（Party）** | 跟診所有關係的人或單位，一人一筆 | L1 ① |
| **參與（Engagement）** | 某對象在某條業務線裡的一次參與 | L2 |
| **資料等級（L0–L3）** | 對象的資料完整度，決定他能做什麼 | L1 ① |
| **資源（Resource）** | 總量固定的東西：場地、人、設備 | L1 ② |
| **佔用（Hold）** | 某資源在某時段被佔住的事實 | L1 ② |
| **預約（Booking）** | 業務層面的約定，會造成一或多筆佔用 | L2 |
| **帳目（Ledger Entry）** | 帳本上的一列：日期、金額、名目、付款方 | L1 ③ |
| **名目（Fee Item）** | 收費項目主檔，收據與報表的分類軸 | L1 ③ |
| **外部給付方（Funding Provider）** | 代付一部分錢的第三方，可插拔 | L1 ③ 擴充點 |
| **報價快照** | 當時算出的金額，之後不因規則改變而重算 | L1 ③ |
| **中介模組** | 被多條流程共用、規則來自外部、變動頻繁的模組 | L1.5 |
| **核銷案** | 向給付方請款的過程容器，收納的是帳目 | L1.5 |
| **認列** | 服務發生的時點，收入歸屬的月份，永不改 | L1 ③ |
| **入帳** | 錢實際進入銀行或現金的時點與金額，永不改 | L1 ③ |
| **核減** | 給付方核准金額少於申請金額的差額，需有明確紀錄 | L1 ③ |
| **反向更正** | 更正錯誤的方式：記一筆相反的列，不改原列 | L1 ③ |
| **只增不改** | 帳本的列寫下即不可修改 | L1 紀律 |
