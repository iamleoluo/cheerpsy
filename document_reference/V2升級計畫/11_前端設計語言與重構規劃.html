0這份文件解決什麼問題

需求是「前端不夠直覺、不夠好看，像是為了配合後端才長成這樣」。掃過 apps/web/src 全部 33 頁之後的結論是：問題不是美感，是少了一層。

最能說明問題的一個數字globals.css 全檔只有 @tailwind 三行——零個設計 token。這代表每一個頁面作者都得自己決定卡片長什麼樣、表頭多大、「未收」是哪一種紅。結果是 54 份手寫 <table>、40 個手寫 modal、30 種卡片、73 個彩色主按鈕，而同一個「未收 / 未到 / 逾期」語意散成五個紅色階。這種情況下，不管誰來寫、寫得多用心，都不可能一致。

1.4 沒有資料層，失敗被偽裝成沒資料

204 次裸 clientFetch、669 個 useState，沒有快取，也沒有共用的載入／錯誤／空白約定。多數頁面寫的是 .catch(() => setRows([]))。

實測撞到的狀況撰寫本文件期間 session 過期，打開 /rooms，畫面永遠停在「載入診間中…」——console 裡是 9 個 401，但畫面完全沒有說發生什麼事。櫃檯主控台整頁死掉而使用者只會覺得「系統很慢」。在財務畫面上，把失敗顯示成「沒有資料」比顯示錯誤更危險。

2設計語言

v7 原型裡診療所自己改出來的那幾條規則，其實已經構成一套完整的視覺語言。把它寫成 token，就不用每頁重新發明。

2.1 核心規則：顏色只表達狀態，不表達操作

這條是 v7 診間日曆定案第 ③ 條的原話「已到／未到按鈕改為中性黑白，狀態改由右上角小圖示標色」。在一天要掃 38 格的密集畫面上，如果按鈕也有顏色，眼睛就沒辦法用顏色掃狀態了。
現在系統裡有 73 個彩色主按鈕，正好違反這條。

配套的是定案第 ④ 條：已完成（報到＋收款）整格轉灰。灰色不是「不重要」，而是「這格今天不用再碰了」——對櫃檯來說這比「已完成」有用得多。這兩條合起來就是整套語言的地基。

5資料層

204 次裸 fetch、669 個 useState，缺的是中間那一層。

要建的東西解決什麼
useApi()一個 hook 收掉快取、重新驗證、載入態。頁面不再自己管 loading/error/data 三個 state
401 統一處理目前 token 過期會讓 /rooms 永遠停在「載入診間中…」（§1.4 實測）。應該是：靜默續期，失敗才導回登入並記住原本要去哪
AsyncBoundary強制每個資料區塊都有三態：載入＝骨架屏（不是空白）、錯誤＝說明＋重試鍵、空白＝說明＋下一步
型別從後端生成每頁手抄 interface 是 09 §5 那些後端變更會漏改前端的原因。用 FastAPI 的 OpenAPI schema 生一份，改壞了 tsc 就會擋下
為什麼 .catch(() => setRows([])) 在這個系統特別危險把失敗顯示成「沒有資料」，在財務畫面上等於謊報。行政看到應收帳冊空的，會以為今天都收完了。三態約定不是體驗優化，是正確性要求。

7.3 這份文件的立場

不是換皮，是補一層如果只做 P2（把三頁畫得好看），沒有 P0 的 token 與 P1 的元件庫，三個月後會再長出第 55 份手寫 <table> 與第 6 種紅色。順序不能顛倒的理由就在這裡：P0/P1 不改變任何畫面，但它們決定了 P2 之後的每一頁能不能保持一致。
