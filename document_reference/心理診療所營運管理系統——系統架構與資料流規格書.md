# 心理診療所營運管理系統——系統架構與資料流規格書

## 一、系統架構定位

這是一個**事件驅動的單一資料源系統**，採三層架構：

- **輸入層**：心理師對預約的兩個動作（建立、取消）是系統唯一的人為主要資料輸入點，行政只做維度資料維護與狀態確認
- **事件層**：預約狀態的變化驅動下游所有資料寫入，多數透過排程觸發（非即時）
- **衍生層**：流水帳、財務核銷、月報表皆為對預約事件的不同維度聚合，本身不接受直接輸入

這個定位決定了三個關鍵特性：
1. 資料一致性由「單一資料源 + 不可逆狀態流轉」保證，而非靠校驗
2. 帳務可信度來自時間鎖定，而非權限控制（管理者修改是稽核例外，不是常規路徑）
3. 系統複雜度集中於排程與狀態機，前端極簡

## 二、核心資料模型

### 2.1 資料表清單

| 表名 | 性質 | 寫入來源 | 寫入頻率 |
|------|------|----------|---------|
| `cases`（個案） | 維度表 | 行政手動建立 | 低頻（初診時） |
| `appointments`（預約） | 核心事實表 | 心理師手動建立 | 中頻 |
| `sessions`（諮商紀錄／流水帳） | 衍生事實表 | 日結排程 | 每日批次 |
| `room_occupancy`（空間佔用） | 物化視圖 | `appointments` 觸發 | 隨預約即時 |
| `invoices`（收據） | 交易表 | 行政產製、自動轉單 | 中頻 |
| `therapist_payouts`（心理師酬勞發放） | 交易表 | 行政月結手動 | 低頻 |
| `petty_cash`（零用金紀錄） | 獨立帳 | 行政手動 | 中頻 |
| `audit_log`（稽核軌跡） | 紀錄表 | 系統自動 | 高頻 |
| `reminder_log`（電訪追蹤） | 紀錄表 | 行政手動 | 中頻 |

### 2.2 主要欄位與關係

**`cases`**
- 主鍵：`case_id`
- 加密欄位：`national_id`（應用層 AES，金鑰不存於 DB）
- 外鍵：`therapist_id`
- 關鍵維度：`funding_source`（自費／機構轉介）、`institution`、`status`

**`appointments`**
- 主鍵：`appointment_id`，格式 `R-YYYYMMDD-{therapist_code}-{seq}`
- 外鍵：`case_id`、`therapist_id`、`room_id`（可 null，線上／家訪不需）
- 狀態欄位：`status`（已建立／已執行／已取消）
- 金額欄位：`amount`（批次建立時可個別覆寫）
- 衍生欄位（查詢時計算，不儲存）：`therapist_share`、`clinic_share`

**`sessions`**
- 主鍵：`session_id`
- 外鍵：`appointment_id`（1:1 永久關聯）、`invoice_id`（收據產製後回寫）
- 不可變欄位：日期、心理師、個案、金額、抽成 → 一旦寫入只能由管理員修改並留 audit

**`room_occupancy`**
- 複合鍵：`(date, time_slot, room_id)`
- 外鍵：`appointment_id`
- 性質：可由 `appointments` 推導，但為查詢效能物化儲存

**`invoices`**
- 主鍵：`invoice_id`，格式 `I-YYYYMMDD-{therapist_code}-{seq}`
- 外鍵：`appointment_id`、`session_id`
- 狀態：`status`（有效／作廢），作廢時保留紀錄，編碼軌跡不釋出

## 三、資料流向

```
[心理師輸入]                  [行政輸入]              [系統排程器]
      │                          │                        │
      ▼                          ▼                        ▼
  appointments ──→ room_occupancy   cases             (每日凌晨)
      │                                                    │
      │ (T+1 結算)                                          │
      └────────────────────────────────────────────────────►  sessions
                                                              │
                                                              ├─► 自費分支 ──► 待收款清單
                                                              │                │
                                                              │                ▼ (行政確認)
                                                              │                payment_status = paid
                                                              │
                                                              └─► 機構分支 ──► 請款池
                                                                               │
                                                                               ▼ (行政批次)
                                                                               待請款 → 請款中 → 已核銷

(每月排程)
   sessions + invoices + petty_cash + therapist_payouts ──► monthly_report
```

關鍵性質：
- **資料只能單向往下流動**：`appointments` → `sessions` → 財務狀態 → 月報表
- **物化視圖可重建**：`room_occupancy` 若損毀可由 `appointments` 完全重建
- **月報表是查詢結果**：是否落地為快照取決於是否需要回溯歷史時點

## 四、狀態機

### 4.1 預約狀態機（系統核心）

| 起始狀態 | 觸發事件 | 觸發來源 | 終止狀態 | 副作用 |
|----------|----------|---------|----------|--------|
| —— | 建立預約 | 心理師（同步） | 已建立 | 寫入 `room_occupancy` |
| 已建立 | 當日內取消 | 心理師（同步） | 已取消 | 釋出 `room_occupancy`、寫入 `audit_log` |
| 已建立 | T+1 結算 | 排程器（每日） | 已執行 | 寫入 `sessions`、產生金流追蹤項 |
| 已執行 | 管理者強制修正 | 管理員（例外） | 任意 | 必填修改原因，寫入 `audit_log` |
| 已取消 | （終態） | —— | —— | —— |

**設計重點**：從「已建立」到「已執行」是**被動觸發**（時間到期），不是主動操作。心理師若不在當日取消，系統將其視為已執行。舉證責任落在操作者，避免日後爭議。

### 4.2 個案狀態機

| 狀態 | 進入條件 | 觸發來源 |
|------|---------|---------|
| 初診 | 個案首次建立 | 行政手動 |
| 持續諮商 | 第二次預約建立 | 系統自動 |
| 暫停中 | 行政手動標記 | 行政 |
| 已結案 | 行政手動標記 | 行政或心理師 |
| 流失 | 超過 N 日無新預約且未結案 | 排程器（每日） |

### 4.3 付款／請款狀態機（綁定於 `sessions`）

依 `cases.funding_source` 分流：

**自費**：`未付款` → `已付款`（行政確認收訖）

**機構**：`待請款` → `請款中`（批次送出時）→ `已核銷`（撥款到帳時）

每次轉換都寫入時間戳記，作為金流時差分析的資料基礎。

## 五、事件與觸發機制

### 5.1 同步事件（即時）

| 事件 | 來源 | 影響的資料表 |
|------|------|------------|
| 預約建立 | 心理師 | `appointments`、`room_occupancy` |
| 預約取消 | 心理師 | `appointments`、`room_occupancy` |
| 收據產製 | 行政 | `invoices`、`sessions.invoice_id` 回寫 |
| 付款確認 | 行政 | 付款狀態欄位更新 |
| 零用金支出 | 行政 | `petty_cash` |

### 5.2 排程事件

| 事件 | 頻率 | 內容 |
|------|------|------|
| 日結批次 | 每日凌晨（建議 03:00） | 掃描前一日「已建立」狀態的預約，轉為「已執行」並寫入 `sessions` |
| 流失預警掃描 | 每日 | 比對 `cases` 的最後預約日，超過門檻者標記 |
| N 日後門診彙整 | 每日 | 產出供行政電訪的名單 |
| 月結報表 | 每月 1 號（或設定日） | 計算上月所有指標，決定是否落地為快照 |

### 5.3 排程設計關鍵考量

- **日結時間點**需早於任何使用者可能操作的時間，避免狀態競爭
- **月結建議落地為快照表**：「墊付金額」會隨後續請款進度變動，若不快照，回頭看歷史報表會產生不一致
- 若實作於 Google Sheets / Notion，無法做真正的排程，需以「手動觸發 + 確認彈窗」模擬，並接受時間精度損失

## 六、衍生欄位與計算邏輯

以下欄位**不儲存**，皆由查詢時即時計算，避免資料不一致：

| 衍生欄位 | 公式 | 計算時機 |
|---------|------|---------|
| 心理師應得酬勞 | `amount × 0.7` | 查詢時 |
| 診所應得收入 | `amount × 0.3` | 查詢時 |
| 空間稼動率 | `已執行場次 / 可用時段總數` | 報表查詢時 |
| 取消率 | `已取消數 / 建立總數` | 報表查詢時 |
| 個案續診率 | `本月有預約且非首次的個案 / 本月有預約的個案` | 報表查詢時 |

### 墊付金額（核心 KPI）

```
墊付金額 = Σ(已付給心理師、但對應請款尚未核銷的酬勞)
```

實作上需要兩個資料交集：
- `therapist_payouts`：每筆酬勞付款的明細，能反查到對應的 `sessions`
- `sessions` 的請款狀態

**這要求心理師酬勞發放時要建立 `payout_id ↔ session_id` 的多對多關聯**。若只記月度總額不記明細，無法計算墊付，是設計上必須注意的隱性需求。

## 七、權限與資料隔離

### 7.1 權限矩陣

| 動作 | 心理師 | 行政 | 管理員 |
|------|-------|------|-------|
| 建立／當日取消預約 | ✓（限本人） | ✓ | ✓ |
| 修改已結算紀錄 | ✗ | ✗ | ✓（必附原因） |
| 查看個案聯絡資訊 | ✗ | ✓ | ✓ |
| 查看諮商摘要 | ✓（限本人個案） | ✗ | ✓ |
| 查看本人收入分析 | ✓ | ✗ | ✓ |
| 查看全所財務 | ✗ | 部分 | ✓ |
| 產製收據／核銷 | ✗ | ✓ | ✓ |
| 零用金登載 | ✗ | ✓ | ✓ |

### 7.2 隔離實作要點

- 心理師端所有查詢強制加 `WHERE therapist_id = current_user_id`，在 ORM 或中介層強制注入
- 行政端對諮商摘要欄位的存取應在 DB 層阻擋（row-level security），不只前端隱藏
- 加密欄位的加解密在應用層處理，金鑰不放於 DB

## 八、稽核與不可變性

### 8.1 不可變資料

- `sessions` 全表（日結後）
- `invoices` 已產製紀錄（只能標記作廢）
- `audit_log` 全表（only-append）

### 8.2 `audit_log` 寫入規格

每筆必含：
- 原始值（JSON 快照）
- 修改後值（JSON 快照）
- 時間戳記
- 操作者 ID
- 修改原因（管理員修改時必填）
- 來源動作類型（手動／系統）

月報表的「帳務修改紀錄」段落直接從 `audit_log` 撈取。

## 九、資料長度與分區

### 9.1 預約與空間資料

`room_occupancy` 是查詢密集表（每次開啟空間預約表都要掃），需分區：
- 在正式 DB 採按月 partition
- 在 Sheets / Notion 等平台則需手動拆表（年或月為單位）

### 9.2 歷史封存

三層儲存策略：
- **熱**：當月 + 未來預約，常駐主查詢路徑
- **溫**：當年內歷史，可查詢但不索引高頻欄位
- **冷**：跨年資料，供月報表回溯與稽核

## 十、技術實作選項

| 選項 | 排程 | 權限隔離 | 加密 | 稽核 | 適用情境 |
|------|------|---------|------|------|---------|
| Google Sheets + Apps Script | 弱 | 弱（檔案級） | 手刻 | 手刻 | 早期試行、流程驗證 |
| Notion Database | 無 | 中（page 級） | 無 | 弱 | 概念驗證，不適合正式上線 |
| Airtable / SeaTable | 中 | 中 | 弱 | 中 | 中期過渡 |
| 自建（Postgres + Next.js 等） | 強 | 強 | 強 | 強 | 正式上線 |

從本系統需求（多角色權限、加密、排程準確性、稽核完整性）來看，**最終必然走向自建**。前期可用 Sheets 試行流程，但要意識到 Sheets 無法滿足權限隔離與排程準確性，遷移時資料需重整。

## 十一、與業務文件的視角對照

| 業務文件視角 | 技術視角 |
|------------|---------|
| 模組三（流水帳）與模組五（核銷報表） | 同一張 `sessions`，不同查詢視角 |
| 模組四（空間預約表） | `room_occupancy` 物化視圖，可由 `appointments` 重建 |
| 模組七（月報表） | 查詢結果，是否落地為快照是設計選擇 |
| 「預約狀態流轉」 | 同步事件 + T+1 排程事件的組合 |
| 「帳務鎖定」 | 業務規則層 + DB 約束 + audit 三層防護 |

## 十二、技術層面的待確認事項（補原文件之外）

| 技術議題 | 影響 |
|---------|------|
| 系統實作平台 | 影響排程、權限、加密的實作難度 |
| `therapist_payouts` 與 `sessions` 的關聯設計 | 影響墊付金額能否計算 |
| 跨年資料是真分區或手動拆表 | 影響歷史查詢效能與維護成本 |
| 請款觸發方式（人工 vs 自動） | 影響是否需新增「請款待確認」中間態 |
| 收據作廢的編碼策略（gap／重用／標註） | 影響稅務查核時的編碼軌跡完整性 |
| 月報表是否快照落地 | 影響歷史報表的時點一致性 |
| 排程器選型（cron / 雲端排程 / 應用內 scheduler） | 影響日結準時性與故障重試機制 |
